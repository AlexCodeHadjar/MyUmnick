# application/pipeline — конвейер ответа: LLM → разбор тегов → нарезка фраз → TTS

## Ответственность
Превращает поток дельт LLM в то, что нужно потребителям: текст для чата, текст для озвучки,
события эмоций, текст для истории. Сейчас — разбор потока (`StreamParser`); далее —
`ReplyPipeline` (S-3.4) и `SentenceChunker` (S-7.2). НЕ строит промпт, не хранит историю,
не нормализует числа для TTS (S-7.2), не знает о WebSocket.

## Публичный API (`__init__.py`)
| Символ | Назначение |
|---|---|
| `StreamParser` | `feed(delta) → [ParseEvent]`, `flush() → [ParseEvent]`, `full_text` |
| `TextDelta` | `text` (чат) и `spoken_text` (TTS: без эмодзи и разметки) |
| `EmotionCue` | Известный тег эмоции; `spoken_text == ""` |
| `ParseEvent` | `TextDelta \| EmotionCue` |
| `HOLD_LIMIT` | Максимум символов незакрытого «<», которые придерживаются (32) |

## Инварианты (тесты `tests/unit/application/pipeline/test_stream_parser.py`)
- Склейка `text` всех событий == вход без тегов — при любом разбиении на дельты (property).
- Последовательность `EmotionCue` == известные теги входа по порядку; неизвестные теги
  выбрасываются.
- `<` не в форме `<слово>` — текст: «3 < 5 > 2», «а <б в», «x<y» доходят до чата как есть.
- В конце потока недописанный известный тег (`<hap`) выбрасывается; одиночное «<» и «<y» — нет.
- Текст без «<» отдаётся сразу, без задержки (T-01).

## Производительность
- Горячий путь: да. `feed` — O(длина дельты + придержанный хвост ≤ 32 символов), одна
  регулярка на порцию для `spoken_text`.

## Как расширять
- Новая эмоция — только в `domain.Emotion`; разбор подхватит её автоматически.
- Числа и сокращения для TTS — нормализатор S-7.2 поверх `spoken_text`, не здесь.
