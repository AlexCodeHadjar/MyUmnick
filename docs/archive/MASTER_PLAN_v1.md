## 1. Развёрнутая постановка задачи (подробный промт)

Ниже — исходная идея, переписанная в формат технического задания. Этот блок можно целиком давать
ИИ-ассистенту как вводную к проекту.

### 1.1 Цель

Создать настольное приложение (Windows в первую очередь, с возможностью переноса на Linux),
в котором:

- справа отображается анимированная модель витюбера (Live2D, в перспективе VRM);
- слева — чат с этой моделью;
- «мозг» витюбера — локальная языковая модель (LLM), работающая без интернета;
- витюбер отвечает текстом и голосом, двигает ртом синхронно с речью и меняет эмоции по смыслу
  ответа;
- главная характеристика продукта — скорость реакции: пользователь должен ощущать живой диалог,
  а не «запрос → ожидание → ответ».

### 1.2 Функциональные требования

| ID | Требование | Этап |
|---|---|---|
| FR-01 | Окно приложения: чат слева, сцена с моделью справа, разделитель с изменяемой шириной. | 5 |
| FR-02 | Ввод текстового сообщения, отправка по Enter, перенос строки по Shift+Enter. | 5 |
| FR-03 | Ответ отображается потоково (по токенам), а не целиком в конце. | 2–5 |

### 1.4 Ограничения

- Только локальные модели. Облачные API допустимы лишь как необязательный адаптер для сравнения

- Потребительское железо: одна видеокарта 8–16 ГБ VRAM (подробнее — раздел 13).
- Основной язык общения — русский (влияет на выбор LLM, TTS и STT).

### 1.5 Что не входит в MVP

- Дообучение (fine-tune) собственной модели.
- Собственный движок рендера аватара.
- Трекинг лица через веб-камеру.
- Мультиплатформенные сборки (Linux/macOS) — после релиза 1.0.

## 2. Анализ идеи

### 2.1 Что это на самом деле

«Витюбер с чатом» — это не одна программа, а пять подсистем и дирижёр между ними:

```text
┌──────────────────────────────────────────────────────────────────┐
│                       ДИРИЖЁР (оркестратор)                       │
│  принимает реплику → строит промпт → запускает конвейер ответа     │
│  → раздаёт текст, эмоции, звук → следит за отменой и метриками     │
└───────┬───────────┬────────────┬────────────┬────────────┬───────┘
        │           │            │            │            │
   ┌────▼───┐  ┌────▼────┐  ┌────▼────┐  ┌────▼────┐  ┌────▼─────┐
   │  LLM   │  │  Голос  │  │  Аватар │  │   UI    │  │  Память  │
   │(мозг)  │  │TTS / STT│  │ Live2D  │  │  чат    │  │ кратк./  │
   │        │  │         │  │ липсинк │  │         │  │ долгоср. │
   └────────┘  └─────────┘  └─────────┘  └─────────┘  └──────────┘
```

Каждая подсистема по отдельности — решённая задача (есть готовые движки). Вся сложность —
в дирижёре: как соединить их так, чтобы задержки не складывались, а перекрывались. Именно поэтому
скорость здесь — вопрос архитектуры, а не «быстрой видеокарты».

### 2.2 Сильные стороны идеи

- **Локальность:** приватность, нет платы за токены, нет лимитов, работает офлайн, нет сетевой
  задержки до облака.
- **Чёткий вертикальный срез:** уже после Этапа 5 есть работающий продукт (текстовый чат
  с моделью), дальше — наращивание.
- **Естественная модульность:** подсистемы почти не пересекаются, их легко изолировать за
  интерфейсами.
- **Хороший полигон для дисциплины:** проект большой, но разбивается на независимые куски,
  удобные для сессионной работы с ИИ.

### 2.3 Главные сложности (и где они решаются)

| Сложность | Почему это проблема | Решение | Раздел |
|---|---|---|---|
| Сложение задержек | LLM + TTS + воспроизведение последовательно дают 3–6 с | Стриминг и конвейер по фразам: TTS начинает первую фразу, пока LLM пишет вторую | 3, 5.6 |
| Конкуренция за GPU | LLM и TTS на одной видеокарте мешают друг другу | LLM — на GPU, быстрый TTS — на CPU; тяжёлый TTS — опция | 3.4, 4 |
| Русский язык у малых моделей | 7–8B модели хуже держат грамматику и факты | Отбор модели бенчмарком качества+скорости, RAG, короткие ответы | 10 (Этапы 2, 10) |
| Синхронизация текст/звук/рот | Текст бежит быстрее голоса, рот должен совпадать со звуком | Липсинк считается в UI из реально играющего звука; режим «субтитров» | 5.13, Этап 7 |
| Мгновенная отмена | Генерация и синтез продолжаются «в пустоту» | Единая модель отмены через отмену asyncio-задач и закрытие потоков | 5.14 |
| Размер проекта | Код расползается, ИИ теряет контекст | Жёсткие правила, архитектурные контракты в CI, сессионный протокол | 7, 9 |
| Лицензии | Live2D SDK и часть голосовых моделей имеют ограничения | Проверка лицензий на Этапе 0, фиксация в `docs/licenses.md` | 4.4 |

### 2.4 Ключевые архитектурные решения (кратко)

- **Три процесса:** UI (Tauri + веб-фронтенд), Ядро (Python, asyncio), LLM-сервер (llama.cpp).
  Падение одного не валит остальные; LLM-сервер заменяем.
- **Гексагональная архитектура в ядре:** домен не знает ни про llama.cpp, ни про WebSocket,
  ни про Silero.
- **Горячий путь — на асинхронных очередях**, управляющие события — через шину событий.
- **Звук играет UI, он же считает липсинк** — синхронизация «бесплатна» и точна.
- **Стабильный префикс промпта** для переиспользования KV-кэша LLM.
- **Единый источник схемы протокола** (Python-модели → JSON Schema → TypeScript-типы).
- **Плагины через реестр и точки расширения**, без правки ядра.

### 2.5 Чего сознательно не делаем

- Не используем тяжёлые LLM-фреймворки в горячем пути (цепочки, агенты «из коробки»): они
  добавляют непрозрачные слои, задержку и усложняют контроль. Свой тонкий слой через порты —
  200–300 строк, полностью под контролем.
- Не дробим на микросервисы. Три процесса — достаточно. Каждый лишний межпроцессный переход —
  это сериализация и задержка.
- Не пишем свой рендерер Live2D/VRM — используем готовые.
- Не дообучаем модель до тех пор, пока бенчмарки не покажут, что промпт + RAG исчерпали себя.
- Не оптимизируем «на глаз»: любая оптимизация — только после замера и с замером после.

### 2.6 Определение успеха

Проект считается успешным, если:

1. На эталонном железе (раздел 13) выполняются NFR-01…NFR-05.
2. На эталонном наборе вопросов (раздел 11.4) доля правильных ответов не ниже порога, выбранного
   на Этапе 2 (стартовый ориентир — 80 %).
3. Новый TTS-движок подключается за одну сессию ИИ без изменения кода вне своего адаптера.
4. ИИ-ассистент начинает продуктивную работу в новой сессии, прочитав не более ~6 файлов
   документации.

## 3. Скорость — главный приоритет

### 3.1 Анатомия задержки

Наивная (последовательная) схема:

```text
Пользователь нажал Enter
│
├─ сборка промпта ............ 5 мс
├─ prefill LLM (весь контекст) 400–1500 мс   ← пересчитывается каждый раз
├─ генерация всего ответа .... 1500–4000 мс  ← ждём конец
├─ синтез всего ответа ....... 800–3000 мс   ← ждём конец
└─ начало звука .............. ИТОГО 3–8 секунд  ✗
```

Целевая (конвейерная) схема:

```text
Enter ─┬─ аватар: анимация «думаю» ............................ ~16 мс (1 кадр)
       ├─ сборка промпта (префикс уже в KV-кэше) .............. ≤ 5 мс
       ├─ prefill только новых токенов ......................... 30–100 мс
       ├─ ПЕРВЫЙ ТОКЕН на экране (TTFT) ........................ ≤ 250 мс
       ├─ первая фраза готова (4–8 слов) ....................... +150–300 мс
       ├─ TTS первой фразы ..................................... +100–250 мс
       └─ ПЕРВЫЙ ЗВУК (TTFA) ................................... ≤ 800 мс  ✓
             │
             └─ пока звучит фраза 1: LLM пишет фразу 2, TTS синтезирует её
                → звук идёт без пауз
```

Ключевая идея: задержки не складываются, а перекрываются. Пользователь ждёт только «голову»
конвейера, всё остальное делается, пока он слушает.

### 3.2 Метрики

| Метрика | Определение | Зачем |
|---|---|---|
| TTFT | От отправки сообщения до первого видимого токена | Ощущение «она меня услышала» |
| TTFS | До первой готовой фразы для TTS | Показывает, правильно ли режется текст |
| TTFA | До первого сэмпла звука в динамике | Главная метрика «живости» |
| TPS | Токенов в секунду при генерации | Хватает ли скорости, чтобы звук не прерывался |
| RTF | Real-Time Factor TTS (время синтеза / длительность звука) | Должен быть < 0.3, иначе голос будет «заикаться» |
| Gap | Паузы между фразами при воспроизведении | Должны быть ≈ 0 (кроме естественных) |
| Cancel latency | От «Стоп» до тишины и остановки генерации | NFR-04 |
| E2E | До конца ответа | Вторична, но отслеживается |

Условие непрерывной речи: скорость генерации текста должна быть выше скорости произнесения.
Русская речь — примерно 2.5–3.5 токена/с на слух, поэтому даже 25–30 ток/с дают запас ×8.
Реальное узкое место — не TPS, а TTFT и TTS первой фразы.

### 3.3 Бюджет задержки (TTFA ≤ 800 мс)

| Стадия | Бюджет | Кто отвечает |
|---|---|---|
| UI → Ядро (WebSocket, localhost) | ≤ 3 мс | gateway |
| Валидация и маршрутизация | ≤ 2 мс | application/conversation |
| Решение «нужен ли RAG» + поиск | ≤ 40 мс (0 мс, если не нужен) | application/memory |
| Сборка промпта | ≤ 5 мс | application/prompting |
| Prefill новых токенов (префикс в кэше) | ≤ 100 мс | LLM-сервер |
| Генерация первой фразы | ≤ 300 мс | LLM-сервер + SentenceChunker |
| TTS первой фразы | ≤ 250 мс | adapters/tts |
| Ядро → UI (бинарный аудиокадр) | ≤ 5 мс | gateway |
| Буфер воспроизведения WebAudio | ≤ 40 мс | ui/features/audio |
| **Итого** | **≈ 750 мс** | |

Бюджет — это контракт: бенчмарк Этапа 9 проверяет каждую строку, CI падает при превышении p95
более чем на 15 %.

### 3.4 Техники ускорения

Каждая техника привязана к этапу, где она реализуется.

**⏱ T-01. Стриминг везде (Этапы 2–7).** LLM отдаёт токены потоком (SSE), ядро сразу пересылает
их в UI, UI отрисовывает. Ни одна стадия не ждёт полного результата предыдущей.

**⏱ T-02. Конвейер по фразам с «агрессивной» первой фразой (Этап 7).** Поток токенов режется на
фразы (`SentenceChunker`). Каждая фраза сразу уходит в TTS. Первая фраза отрезается раньше
обычного — по запятой уже после 4 слов, — чтобы звук начался как можно быстрее. Последующие
фразы режутся длиннее (по точке или по запятой после ~10 слов) — так интонация естественнее.

**⏱ T-03. Стабильный префикс промпта → переиспользование KV-кэша (Этап 3).** LLM-сервер
(llama.cpp) хранит KV-кэш предыдущего запроса и пересчитывает только отличающийся «хвост».
Поэтому промпт строится строго в порядке «от неизменного к изменчивому»:

```text
[системный промпт персоны]            ← не меняется никогда за сессию
[сжатое резюме старой части диалога]  ← меняется редко (см. T-04)
[история последних N ходов]           ← только дописывается в конец
[динамический блок: время, найденные факты]  ← прямо перед репликой
[реплика пользователя]
```

Ошибка, убивающая кэш: вставлять текущее время или результаты поиска в системный промпт. Тогда
префикс меняется каждый ход, и prefill всего контекста повторяется заново (сотни миллисекунд).

**⏱ T-04. Блочное усечение истории (Этап 3).** Когда история превышает бюджет токенов, её нельзя
сдвигать «по одному сообщению» — это меняет префикс каждый ход. Правильно: при достижении лимита
отрезать сразу большой блок (например, старшую половину), заменить его резюме и дальше снова
только дописывать. Кэш инвалидируется раз в десятки ходов, а не каждый ход.

**⏱ T-05. Предзаполнение во время набора — speculative prefill (Этап 9).** Пока пользователь
печатает, UI с дебаунсом (~300 мс) шлёт событие `input.typing` с текущим текстом. Ядро
отправляет в LLM-сервер запрос на прогрев кэша (prefill без генерации). Когда пользователь
нажмёт Enter, большая часть промпта уже в KV-кэше. Для голосового ввода то же делается по
промежуточным результатам распознавания.

**⏱ T-06. Прогрев при старте (Этап 2).** После загрузки модели выполняется холостой запрос
с системным промптом персоны — первый реальный ответ не платит за «холодный» старт CUDA-ядер
и за prefill системного промпта. То же для TTS: синтез короткой фразы при старте.

**⏱ T-07. Короткие ответы по умолчанию (Этап 3).** Персона инструктирует отвечать
1–3 предложениями, если пользователь не просит подробностей; `max_tokens` ограничен. Живой
диалог — это короткие реплики. Это одновременно и скорость, и естественность.

**⏱ T-08. Без «размышлений» в горячем пути (Этап 2).** Если выбранная модель умеет
reasoning-режим (скрытые рассуждения перед ответом), в диалоге он отключается: рассуждения — это
сотни невидимых токенов до первого видимого. Режим можно включать точечно для сложных вопросов
(маршрутизация на Этапе 10).

**⏱ T-09. Speculative decoding (Этап 9).** llama.cpp умеет использовать маленькую «черновую»
модель того же семейства для ускорения генерации. Даёт прирост TPS 1.3–2× на типичных диалогах.
Включается флагом, проверяется бенчмарком (на некоторых связках выигрыша нет).

**⏱ T-10. Квантизация и полная выгрузка на GPU (Этап 2).** GGUF Q4_K_M / Q5_K_M, все слои на GPU
(`-ngl 99`), Flash Attention включена, размер контекста — не больше необходимого
(8–16 тыс. токенов): огромный контекст съедает VRAM и замедляет prefill.

**⏱ T-11. Разведение ресурсов (Этапы 7, 9).** LLM занимает GPU. Быстрый TTS (Silero/Piper)
работает на CPU и не конкурирует за видеокарту. Если используется тяжёлый TTS на GPU — он
запускается в отдельном процессе, а его VRAM учитывается в бюджете заранее.

**⏱ T-12. Гейтинг поиска по памяти (Этап 10).** Поиск в долговременной памяти выполняется только
если нужен (лёгкий классификатор/эвристика: вопрос о прошлом, о пользователе, «помнишь…»).
Эмбеддинг реплики можно посчитать заранее, во время набора (вместе с T-05).

**⏱ T-13. Фон — только в простое (Этап 10).** Суммаризация истории, извлечение фактов в память,
индексация — фоновые задачи с низким приоритетом. Они запускаются, когда диалог простаивает,
и немедленно отменяются, как только приходит новая реплика.

**⏱ T-14. Мгновенная отмена (Этап 3).** Новое сообщение или «Стоп» отменяет текущий ход целиком:
генерацию (закрытием HTTP-потока — llama.cpp прекращает работу), синтез, воспроизведение. Иначе
следующий ответ ждёт, пока GPU доделает ненужный.

**⏱ T-15. Тонкий горячий путь (Этапы 1, 3).** Токены и аудио идут через `asyncio.Queue` напрямую
между стадиями конвейера, а не через шину событий с подписчиками. Сериализация — orjson.
Логирование на каждый токен — только на уровне DEBUG и выключено по умолчанию.

**⏱ T-16. Батчинг отрисовки в UI (Этап 5).** UI не перерисовывает DOM на каждый токен, а копит
токены и применяет их раз в кадр (`requestAnimationFrame`). Длинная история чата —
виртуализированный список.

**⏱ T-17. Воспринимаемая скорость (Этапы 6, 8).** Аватар реагирует мгновенно: при отправке
сообщения — кивок/анимация «думаю» в том же кадре. Пользователь видит реакцию за 16 мс, даже
если первый звук — через 700 мс. Опционально: если TTFA превышает порог, проигрывается заранее
синтезированное междометие («Хм…», «Так…»).

### 3.5 Как измеряем

- Каждый ход получает `turn_id`. Каждая стадия открывает span
  (`telemetry.span("llm.first_token")`) с `time.perf_counter_ns()`.
- Спаны пишутся в `logs/traces.jsonl` и отправляются в UI на панель метрик (FR-15).
- Скрипт `tools/bench_latency.py` прогоняет эталонный набор реплик и выводит p50/p95 по каждой
  стадии.
- В CI (на машине с GPU или вручную перед релизом) — сравнение с эталоном `bench/baseline.json`;
  регрессия p95 > 15 % = провал.
- Правило: PR, затрагивающий горячий путь, содержит в описании таблицу «до/после».

## 4. Технологический стек

### 4.1 Процессы

```text
┌─────────────────────────────┐   WebSocket (localhost)   ┌──────────────────────────────┐
│  UI-процесс (Tauri 2)       │ ◄──── JSON + бинарь ────► │  Ядро (Python 3.12, asyncio) │
│  ─ окно, чат (Svelte 5)     │                           │  ─ оркестратор, конвейер     │
│  ─ рендер Live2D (PixiJS)   │                           │  ─ память, промпты           │
│  ─ воспроизведение звука    │                           │  ─ TTS / STT (в потоках/     │
│  ─ липсинк (WebAudio)       │                           │    отдельных процессах)      │
└─────────────────────────────┘                           └──────────────┬───────────────┘
                                                                         │ HTTP + SSE
                                                                         │ (OpenAI-совместимый
                                                                         │  API, localhost)
                                                          ┌──────────────▼───────────────┐
                                                          │  LLM-сервер (llama.cpp       │
                                                          │  llama-server, CUDA)         │
                                                          └──────────────────────────────┘
```

Почему LLM-сервер — отдельный процесс:

- это уже максимально оптимизированный C++/CUDA-код — нет смысла тащить его внутрь Python;
- падение/перезапуск модели не роняет приложение;
- смена бэкенда (llama.cpp ↔ Ollama ↔ LM Studio ↔ vLLM) — смена адаптера, а не архитектуры;
- накладные расходы HTTP на localhost — доли миллисекунды, на фоне prefill это ноль.

**Почему ядро на Python:** вся экосистема локального ИИ (TTS, STT, эмбеддинги, VAD) —
Python-first. Тяжёлые вычисления всё равно выполняются в нативном коде (CUDA, ONNX Runtime,
CTranslate2), Python только дирижирует.

**Почему UI на Tauri + веб:** готовые зрелые рендереры Live2D/VRM существуют именно для веба
(PixiJS, three.js); WebAudio даёт точный анализ звука для липсинка; Tauri в разы легче Electron
по памяти и умеет запускать ядро как sidecar-процесс.

выбора UI: протокол WebSocket одинаков для любого клиента.

## 5. Архитектура

### 5.1 Принципы

1. **Гексагональная архитектура (порты и адаптеры).** Ядро приложения (домен + сценарии)
   определяет интерфейсы-порты, внешний мир подключается адаптерами.
2. **Правило зависимостей.** Зависимости направлены только внутрь:
   adapters → application → ports → domain. Домен не импортирует ничего из проекта.
3. **Корень композиции.** Все объекты создаются и связываются в одном месте —
   `bootstrap/container.py`. Нигде больше нет `SomeAdapter()` внутри бизнес-логики.
4. **Данные — очередями, управление — событиями.** Токены и аудио идут по `asyncio.Queue`
   (горячий путь ⏱). Факты вида «ход начался», «эмоция сменилась», «метрика записана» — через
   шину событий.
5. **Всё асинхронно, всё отменяемо, всё измеряемо.** Блокирующие вызовы — только в
   `asyncio.to_thread`/процессах. Каждый ход — отменяемая задача. Каждая стадия — спан
   телеметрии.
6. **Валидация на границах.** Внешние данные (конфиг, сообщения UI, ответы LLM) валидируются один
   раз на входе; внутри домена данные уже корректны и не перепроверяются.

```text
     │ gateway               │               │ adapters               │
```

### 5.5 Порты (пример кода)

```python
# vtuber/ports/llm.py
"""Порт языковой модели: потоковая генерация и прогрев кэша."""
from collections.abc import AsyncIterator
from dataclasses import dataclass
from typing import Protocol

from vtuber.domain.dialogue import Message


@dataclass(frozen=True, slots=True)
class GenerationParams:
    max_tokens: int = 256
    temperature: float = 0.7

        """Отдаёт текстовые дельты. Отмена задачи обязана закрыть поток генерации."""
        ...

    async def prefill(self, messages: list[Message]) -> None:
        """Прогревает KV-кэш без генерации (speculative prefill, T-05)."""
        ...
```

```python
# vtuber/ports/sink.py
"""Куда конвейер отдаёт результаты хода. Конвейер не знает, что за ним — WebSocket, файл или тест."""
from typing import Protocol

from vtuber.domain.emotion import Emotion
from vtuber.domain.speech import AudioChunk


class ReplySink(Protocol):
    async def text(self, delta: str) -> None: ...
    async def emotion(self, emotion: Emotion) -> None: ...

    async def done(self) -> None: ...
```

**Почему Protocol, а не ABC:** структурная типизация — адаптеру не нужно наследоваться от класса
ядра, достаточно иметь нужные методы. Это снижает связанность и позволяет писать тестовые
заглушки в три строки. `mypy --strict` проверяет совместимость.

### 5.6 Конвейер ответа

```python
# vtuber/application/pipeline/reply_pipeline.py
"""Конвейер хода: LLM → разбор тегов → нарезка фраз → TTS. Стадии работают параллельно."""
import asyncio

from vtuber.application.pipeline.chunker import SentenceChunker
from vtuber.application.pipeline.stream_parser import StreamParser
from vtuber.domain.dialogue import Message
from vtuber.kernel.telemetry import span
from vtuber.ports.llm import GenerationParams, LLMPort
from vtuber.ports.sink import ReplySink
from vtuber.ports.tts import TTSPort

_END = None  # маркер конца очереди фраз


class ReplyPipeline:
    def __init__(self, llm: LLMPort, tts: TTSPort, params: GenerationParams) -> None:
        self._llm = llm
        self._tts = tts
        self._params = params

    async def run(self, messages: list[Message], sink: ReplySink) -> str:
        phrases: asyncio.Queue[str | None] = asyncio.Queue()
        async with asyncio.TaskGroup() as tg:
            text_task = tg.create_task(self._write(messages, sink, phrases))
            tg.create_task(self._speak(sink, phrases))
        await sink.done()
        return text_task.result()

    async def _write(
        self, messages: list[Message], sink: ReplySink, out: asyncio.Queue[str | None]
    ) -> str:
        parser, chunker = StreamParser(), SentenceChunker()
        with span("llm.stream"):
            async for delta in self._llm.stream(messages, self._params):
                for event in parser.feed(delta):
                    await event.deliver(sink)
                    for phrase in chunker.feed(event.spoken_text):
                        out.put_nowait(phrase)
        if tail := chunker.flush():
            out.put_nowait(tail)
        out.put_nowait(_END)
        return parser.full_text

    async def _speak(self, sink: ReplySink, phrases: asyncio.Queue[str | None]) -> None:
        while (phrase := await phrases.get()) is not _END:
            with span("tts.phrase"):
                async for chunk in self._tts.synthesize(phrase):
                    await sink.audio(chunk)
```

Что здесь важно:

- `TaskGroup`: если любая стадия падает или ход отменяют — все стадии отменяются автоматически
  (T-14).
- TTS фразы N идёт параллельно с генерацией фразы N+1.
- Конвейер зависит только от портов — его можно полностью протестировать фейковыми
  LLM/TTS/Sink без GPU.

### 5.7 Нарезка фраз (SentenceChunker)

```python
# vtuber/application/pipeline/chunker.py
"""Режет поток текста на фразы для TTS. Первая фраза отрезается раньше (T-02)."""
from collections.abc import Iterator
from dataclasses import dataclass

HARD_STOPS = frozenset(".!?…")
SOFT_STOPS = frozenset(",;:—")


@dataclass(slots=True)
class SentenceChunker:
    first_min_words: int = 4
    next_min_words: int = 10
    _buf: str = ""
    _emitted: int = 0

    def feed(self, text: str) -> Iterator[str]:
        self._buf += text
        while (cut := self._find_cut()) is not None:
            phrase, self._buf = self._buf[:cut].strip(), self._buf[cut:]
            if phrase:
                self._emitted += 1
                yield phrase

    def flush(self) -> str | None:
        phrase, self._buf = self._buf.strip(), ""
        return phrase or None

    def _find_cut(self) -> int | None:
        min_words = self.first_min_words if self._emitted == 0 else self.next_min_words
        for i, ch in enumerate(self._buf):
            followed_by_space = self._buf[i + 1 : i + 2].isspace()
            if ch == "\n" or (ch in HARD_STOPS and followed_by_space):
                return i + 1
            if ch in SOFT_STOPS and followed_by_space and len(self._buf[:i].split()) >= min_words:
                return i + 1
        return None
```

Требование «знак + пробел» не даёт резать `3.5`, `т.е.` в середине и многоточие по частям (ценой
ожидания одного токена). Граничные случаи (сокращения, числа, кавычки, эмодзи) покрываются
тестами, в т.ч. property-based (hypothesis): «склейка всех фраз == исходный текст без лишних
пробелов».

### 5.8 Разбор эмоций в потоке (StreamParser)

LLM инструктируется вставлять теги эмоций прямо в текст: `<happy>Привет! Рада тебя видеть.`
Отдельная модель-классификатор эмоций не нужна — это экономит и время, и VRAM ⏱.

StreamParser:

- принимает дельты токенов (тег может прийти разрезанным: `<ha` + `ppy>`), держит минимальный
  буфер только когда виден незакрытый `<`;
- известные теги превращает в событие `EmotionChanged(Emotion.HAPPY)`, неизвестные — выбрасывает
  (не показывает и не озвучивает);
- отдаёт `display_text` (для чата) и `spoken_text` (для TTS — без тегов, эмодзи и
  markdown-разметки);
- копит `full_text` для истории;
- `feed()` возвращает список событий разбора; у каждого есть `deliver(sink)` (отправить
  текст/эмоцию в sink) и `spoken_text` (что из этого озвучить, может быть пустой строкой) — так
  конвейер не ветвится по типам событий (полиморфизм вместо if/elif).

Формат тегов и список эмоций — в `domain/emotion.py` (единственный источник), промпт персоны
строится из этого же списка, чтобы они не расходились.

### 5.9 Шина событий

```python
# vtuber/kernel/bus.py
"""Шина управляющих событий. НЕ для горячего пути: токены и аудио идут очередями (T-15)."""
import asyncio
from collections import defaultdict
from collections.abc import Awaitable, Callable

type Handler[E] = Callable[[E], Awaitable[None]]


class EventBus:
    def __init__(self) -> None:
        self._handlers: defaultdict[type, list[Handler[object]]] = defaultdict(list)

    def subscribe[E](self, event_type: type[E], handler: Handler[E]) -> None:
        self._handlers[event_type].append(handler)  # type: ignore[arg-type]

    async def publish(self, event: object) -> None:
        await asyncio.gather(*(handler(event) for handler in self._handlers[type(event)]))
```

События — неизменяемые `dataclass(frozen=True, slots=True)` в `domain/events.py`: `TurnStarted`,
`TurnFinished`, `TurnCancelled`, `EmotionChanged`, `MetricRecorded`, `BackendStatusChanged`.
Подписчики — UI-шлюз, планировщик фона, плагины. Это главный механизм расширения: плагин может
реагировать на любое событие, ничего не меняя в ядре (OCP).

### 5.10 Реестр адаптеров и плагинов

```python
# vtuber/kernel/registry.py
"""Реестр фабрик по имени: позволяет выбирать реализацию порта строкой в конфиге."""
from collections.abc import Callable


class Registry[T]:
    def __init__(self, kind: str) -> None:
        self._kind = kind
        self._factories: dict[str, Callable[..., T]] = {}

    def register[F: Callable[..., T]](self, name: str) -> Callable[[F], F]:
        def decorator(factory: F) -> F:
            if name in self._factories:
                raise ValueError(f"{self._kind} '{name}' уже зарегистрирован")
            self._factories[name] = factory
            return factory
        return decorator

    def create(self, name: str, /, *args: object, **kwargs: object) -> T:
        try:
            return self._factories[name](*args, **kwargs)
        except KeyError:
            known = ", ".join(sorted(self._factories))
            raise ValueError(f"Неизвестный {self._kind} '{name}'. Доступны: {known}") from None
```

Использование в адаптере:

```python
@TTS_REGISTRY.register("silero")
class SileroTTS:
    ...
```

Сторонние плагины регистрируются через entry points пакета
(`[project.entry-points."vtuber.plugins"]`), `bootstrap/plugins.py` их загружает при старте.

### 5.11 Корень композиции

```python
# vtuber/bootstrap/container.py
"""Единственное место, где создаются и связываются объекты приложения."""
from vtuber.adapters import LLM_REGISTRY, TTS_REGISTRY
from vtuber.application.conversation import ConversationService
from vtuber.application.pipeline import ReplyPipeline
from vtuber.application.prompting import PromptBuilder
from vtuber.kernel.bus import EventBus
from vtuber.kernel.config import AppConfig


def build_conversation(cfg: AppConfig, bus: EventBus) -> ConversationService:
    llm = LLM_REGISTRY.create(cfg.llm.backend, cfg.llm)
    tts = TTS_REGISTRY.create(cfg.tts.backend, cfg.tts)

```

Нигде, кроме bootstrap, не создаются адаптеры. Тесты собирают тот же граф из фейков.

|---|---|---|

```text

0       1     тип кадра (0x01 = audio)
1       1     версия
2       2     seq (uint16, LE)
4       4     sample_rate (uint32, LE)
```

актуальны. Расхождение типов фронта и бэка становится невозможным.

### 5.14 Жизненный цикл хода и отмена

```text
          chat.send
 IDLE ─────────────────► THINKING ──первый токен──► SPEAKING ──звук закончился──► IDLE
  ▲                         │                          │
  │                         │ chat.cancel / chat.send  │ chat.cancel / chat.send / голос (barge-in)
  │                         ▼                          ▼
  └──────────────────── CANCELLED ◄────────────────────┘
```

- `ConversationService` хранит ссылку на задачу текущего хода. Новый `chat.send` →
  `task.cancel()` → `TaskGroup` конвейера отменяет LLM-стрим (адаптер закрывает HTTP-соединение
  в `async with` — llama.cpp прекращает генерацию) и TTS → UI получает `turn.cancelled`
  и сбрасывает аудиобуфер.
- В историю попадает только произнесённая часть прерванного ответа (с пометкой), чтобы модель
  «знала», что её перебили.
- Состояние хода — явный Enum + таблица переходов; недопустимый переход — исключение в тестах.

### 5.16 Ошибки

- Иерархия доменных ошибок: `VtuberError` → `BackendUnavailable` (`LLMUnavailable`,
  `TTSUnavailable`), `GenerationFailed`, `ConfigError`, `ProtocolError`.
- Адаптер переводит чужие исключения (`httpx.ConnectError`, ошибки torch) в доменные. Код выше
  адаптеров никогда не ловит `httpx.*`.
- Повторы (retry) — только в адаптерах и только для идемпотентных операций; в горячем пути —
  максимум 1 быстрый повтор.
- Ошибка хода не роняет приложение: `ConversationService` превращает её в
  `turn.cancelled(reason)` + сообщение `error` в UI.
- `except Exception` допустим только в одном месте — на верхней границе обработчика хода
  и WebSocket-сессии, с логированием и `turn_id`.

### 5.17 Телеметрия и логи

- structlog → JSON в `logs/app.jsonl`; каждый лог несёт `turn_id` (через contextvars).
- `telemetry.span(name)` — контекстный менеджер, замеряет `perf_counter_ns`, пишет
  в `logs/traces.jsonl` и публикует `MetricRecorded`.
- Уровни: ERROR — сломалось; WARNING — деградация (TTFA выше бюджета, повтор запроса); INFO —
  жизненный цикл (старт, загрузка модели, ход начат/закончен); DEBUG — детали, в т.ч. потоковые
  (выключено по умолчанию).

## 7. Жёсткие правила написания кода

Эти правила обязательны для людей и для ИИ. Всё, что можно проверить автоматически, проверяется
автоматически (линтер, типы, контракты импорта) — CI падает. Остальное проверяется ревью по
чек-листу (7.17) со ссылками на номера правил.

### 7.1 Главный принцип

Каждая строка должна быть необходимой, а каждое имя — понятным. Код пишется так, чтобы его можно
было прочитать один раз и понять, изменить в одном месте и не сломать другое, расширить —
добавлением, а не правкой.

Краткость — не самоцель: если короткая запись читается хуже длинной, выбирается длинная.
«Профессионально» = минимально и очевидно, а не «умно».

| № | Правило |
|---|---|
| R-23 | Не дублировать логику (DRY): повтор из 3+ строк во втором месте → выделяется функция. Но не объединять случайно похожий код с разным смыслом. |
| R-24 | Не писать тривиальные геттеры/сеттеры — используются поля dataclass или `@property` только при вычислении. |

### 7.13 SOLID в этом проекте — конкретно

**S — Single Responsibility (единственная ответственность).** `ReplyPipeline` только соединяет
стадии. Он не режет текст (это `SentenceChunker`), не разбирает теги (`StreamParser`), не знает
о WebSocket (`ReplySink`), не строит промпт (`PromptBuilder`). Каждый из этих классов меняется по
одной причине. Признак нарушения: класс импортирует и httpx, и torch, и websockets.

**O — Open/Closed (открыт для расширения, закрыт для изменения).** Новый TTS = новый файл
в `adapters/tts/` с `@TTS_REGISTRY.register("name")`. Ни одна строка ядра не меняется. Новая
реакция на события (например, отправка эмоции в OBS) = подписчик на `EmotionChanged` в плагине.
Признак нарушения: `if cfg.tts.backend == "silero": ... elif ... == "piper": ...` где-либо вне
реестра.

**L — Liskov Substitution (подстановка).** Любой адаптер `TTSPort` взаимозаменяем: одинаково
реагирует на отмену (закрывает ресурсы, не глотает `CancelledError`), отдаёт PCM в объявленном
`audio_format`, бросает только доменные ошибки. Это закреплено контрактными тестами (R-57),
которые прогоняются для каждого адаптера. Признак нарушения: в конвейере
`if isinstance(tts, PiperTTS): ...`.

**I — Interface Segregation (разделение интерфейсов).** Порты маленькие: `EmbedderPort` (только
embed) отдельно от `MemoryStorePort` (только add/search). `ReplySink` не содержит методов
управления аватаром, которые нужны только UI. Клиент зависит только от того, что использует.
Признак нарушения: фейк для теста приходится заполнять методами `raise NotImplementedError`.

**D — Dependency Inversion (инверсия зависимостей).** application зависит от `LLMPort`
(абстракция, которой владеет ядро), а не от `LlamaCppLLM`. Конкретика подставляется в bootstrap.
Поэтому весь сценарий диалога тестируется за миллисекунды без видеокарты. Признак нарушения:
`from vtuber.adapters...` в application. Ловится import-linter.

### 7.14 Плохо / хорошо

Пример 1. Лишние строки.

```python
# ПЛОХО: 8 строк, сравнение с True, ручной цикл
def get_active(items):
    result = []
    for item in items:
        if item.active == True:
            result.append(item)
    return result

# ХОРОШО: типы, понятное имя, одно выражение
def active_only(items: Iterable[Plugin]) -> list[Plugin]:
    return [item for item in items if item.active]
```

Пример 2. Ветвление по типу вместо полиморфизма (нарушение OCP).

```python
# ПЛОХО
async def speak(cfg: AppConfig, text: str) -> bytes:
    if cfg.tts.backend == "silero":
        model = load_silero()            # и загрузка модели на каждый вызов (R-40)
        return model.apply_tts(text)
    elif cfg.tts.backend == "piper":
        ...

# ХОРОШО: реализация выбрана один раз в bootstrap, здесь — только порт
async def speak(tts: TTSPort, phrase: str, sink: ReplySink) -> None:
    async for chunk in tts.synthesize(phrase):
        await sink.audio(chunk)
```

Пример 3. Вложенность против раннего возврата.

```python
# ПЛОХО
def pick_emotion(tag: str) -> Emotion | None:
    if tag:
        if tag.startswith("<"):
            name = tag.strip("<>")
            if name in Emotion.__members__:
                return Emotion[name]
            else:
                return None
    return None

# ХОРОШО
def pick_emotion(tag: str) -> Emotion | None:
    name = tag.strip("<>").upper()
    return Emotion.__members__.get(name)
```

Пример 4. Перехват отмены.

```python
# ПЛОХО: отмена проглочена — ход «не отменяется», GPU работает дальше
try:
    async for delta in llm.stream(messages, params):
        ...
except Exception:
    log.warning("stream failed")

# ХОРОШО: ловим только то, что умеем обработать; CancelledError пролетает насквозь
try:
    async for delta in llm.stream(messages, params):
        ...
except LLMUnavailable:
    await sink.error(ErrorCode.LLM_DOWN)
    raise
```

Пример 5. Чрезмерная «умность» (нарушение R-33).

```python
# ПЛОХО: формально коротко, фактически нечитаемо
out = [(p, n) for p in ps if (n := len(p.split())) > (4 if not i else 10) or p[-1] in ".!?"]

# ХОРОШО: две строки, но читаются с первого раза
min_words = FIRST_MIN_WORDS if is_first else NEXT_MIN_WORDS
ready = [p for p in phrases if ends_sentence(p) or word_count(p) >= min_words]
```

Пример 6. Голый словарь против структуры.

```python
# ПЛОХО: ключи-строки, опечатка не ловится, тип неизвестен
msg = {"role": "user", "text": text, "ts": time.time()}

# ХОРОШО
@dataclass(frozen=True, slots=True)
class Message:
    role: Role

```

### 7.17 Чек-лист ревью (docs/rules/review-checklist.md)

1. Слой и направление зависимостей верны? (R-01…R-03)
2. Есть ли ветвление по типу/строке бэкенда вне реестра? (OCP, R-07)
3. Можно ли удалить строку без потери смысла? (R-23…R-32)
4. Есть ли «умный» код, который придётся перечитывать? (R-33)
5. Нет ли блокирующих вызовов в корутинах и проглоченной отмены? (R-34, R-38)
6. Все ли внешние вызовы с тайм-аутом и в async with? (R-36, R-37)
7. Ошибки переведены в доменные, сообщения полезны? (R-43, R-45)
8. Тесты проверяют поведение, а не реализацию? Есть контрактный тест для нового адаптера?

| docs/stages/STAGE_NN.md | ИИ + человек | задачи этапа, критерии приёмки, разбивка на сессии | при планировании; галочки — по ходу |
| docs/rules/*.md | все | правила кода и чек-лист | редко, через ADR |
| CHANGELOG.md | человек | изменения по версиям (формат Keep a Changelog) | при релизе |
| docs/user-guide.md | пользователь | настройка персоны, моделей, голоса | Этап 13 |

### 8.2 Принципы

- **Docs-as-code:** документация живёт в репозитории, проходит ревью вместе с кодом.
- **Автогенерируемое не правится руками** и проверяется в CI на актуальность.
- **Один факт — одно место.** Список эмоций — в `domain/emotion.py`; протокол —
  в `gateway/protocol.py`; документы ссылаются, а не копируют.
- **Карточка модуля — контракт.** Если код расходится с карточкой — это баг, исправляется одно
  из двух в том же PR.

## 9. Сессионная работа ИИ-ассистента над кодом

### 9.1 Проблема

В большом проекте ИИ-ассистент в каждой новой сессии начинает «с нуля»: читает десятки файлов,
чтобы понять, где что лежит, тратит на это контекстное окно и время, а к моменту реальной работы
уже забывает начало. Чем больше проект — тем хуже результат.

### 9.2 Принцип: «читай карту, а не территорию»

ИИ получает информацию слоями, от общего к частному, и спускается на следующий слой, только если
предыдущего не хватает:

| Уровень | Что читается | Объём | Когда |
|---|---|---|---|
| 0 | CLAUDE.md / AGENTS.md | ≤ 150 строк | всегда (загружается автоматически) |
| 1 | docs/ai/STATE.md | ≤ 60 строк | всегда, первым действием |
| 2 | docs/stages/STAGE_NN.md текущего этапа | ≤ 200 строк | всегда |
| 3 | docs/ai/PROJECT_MAP.md — нужный раздел (поиском по имени модуля) | 20–50 строк | когда нужно найти символ/модуль |
| 4 | src/vtuber/<module>/README.md — карточки 1–3 модулей из scope | ≤ 80 строк каждая | перед правкой модуля |
| 5 | Конкретные файлы / функции (точечно, по номерам строк из карты) | по необходимости | при правке |

**Бюджет ориентации:** до начала правок ИИ читает не больше ~6 документов (уровни 0–4). Если
этого не хватает — значит, документация неполна, и это первое, что нужно исправить.

### 9.3 Файлы «памяти» проекта

- **CLAUDE.md** (и AGENTS.md для других инструментов — можно сделать одну строку `@AGENTS.md`
  в CLAUDE.md, чтобы не дублировать) — кто ты, приоритеты, ссылки на правила, протокол сессии,
  запреты. Шаблон — 15.1.
- **docs/ai/STATE.md** — «снимок» проекта: текущий этап, последняя завершённая сессия, следующая
  сессия, открытые проблемы, известные ограничения. Перезаписывается (не дописывается!) в конце
  каждой сессии, поэтому всегда короткий. Шаблон — 15.2.
- **docs/ai/PROJECT_MAP.md** — автогенерируемая карта: для каждого пакета — однострочное
  описание (из docstring модуля, R-51) и список публичных классов/функций с `файл:строка`
  и первой строкой docstring. ИИ находит нужное место по карте и открывает файл точно на нужной
  строке.
- **Карточки модулей** — назначение, публичный API, зависимости (порты), события
  (публикует/слушает), инварианты, известные ограничения, «как расширять». Шаблон — 15.4.
- **docs/stages/STAGE_NN.md** — разбивка этапа на сессии S-X.Y, у каждой: цель, scope (список
  файлов/модулей, которые можно трогать), входные документы, критерии готовности. Шаблон — 15.3.
- **docs/ai/sessions/YYYY-MM-DD_S-X.Y.md** — журнал: что сделано, какие решения, какие файлы
  изменены, что осталось, коммиты. Шаблон — 15.5. Журнал — для истории; в рабочую сессию
  читается только последний и только если STATE.md ссылается на него.
- **docs/adr/** — решения. ИИ читает ADR, только если задача касается этого решения (ссылки —
  в карточках модулей).

### 9.4 Протокол сессии

**Старт (≤ 5 минут, ≤ 6 документов):**

1. Прочитать docs/ai/STATE.md → узнать текущую сессию S-X.Y.
2. Прочитать docs/stages/STAGE_X.md → раздел S-X.Y: цель, scope, критерии.
3. Найти в PROJECT_MAP.md модули из scope (поиском, не чтением целиком).
4. Прочитать карточки этих модулей.
5. Кратко изложить план (3–7 шагов) и явно перечислить файлы, которые будут изменены. Если
   в процессе понадобится файл вне scope — остановиться и объяснить почему.

**Работа:**

- Сначала тест (или контрактный тест для адаптера), потом код.
- Читать файлы точечно: поиск по символу → открытие нужного диапазона строк.
- Запускать только релевантные тесты (`pytest tests/unit/application/pipeline`), полный прогон —
  в конце.
- Не «улучшать попутно» код вне scope. Замеченные проблемы — в раздел «Открытые проблемы»
  STATE.md.

**Финиш (обязательный чек-лист):**

- [ ] ruff, mypy, lint-imports, тесты — зелёные.
- [ ] Обновить карточки изменённых модулей.
- [ ] `python tools/gen_map.py` (и `gen_protocol.py`, если менялся протокол).
- [ ] Создать журнал сессии.
- [ ] Перезаписать STATE.md: следующая сессия, новые открытые проблемы.
- [ ] Отметить галочки в STAGE_X.md.
- [ ] Коммит(ы) по Conventional Commits.

### 9.5 Нарезка задач

- Одна сессия = одна задача = один-два модуля. Ориентир — до ~6 изменённых файлов и ~400 строк
  диффа.
- Задача формулируется через результат и критерий: «SentenceChunker режет первую фразу после
  4 слов по запятой; тесты X, Y, Z проходят», а не «поработай над нарезкой».
- Если задача не помещается — она делится ещё до начала сессии (в STAGE_X.md).
- Порядок внутри этапа: порт → фейк → контрактный тест → адаптер → сценарий → интеграция.

### 9.6 Ограничение чтения тяжёлых каталогов

ИИ-инструменту явно запрещается читать то, что не нужно никогда: веса моделей, node_modules,
сборки, логи, lock-файлы, архив. Для Claude Code — правила deny в `.claude/settings.json`
проекта:

```json
{
  "permissions": {
    "deny": [
      "Read(./models/**)",
      "Read(./ui/node_modules/**)",
      "Read(./ui/src-tauri/target/**)",
      "Read(./logs/**)",
      "Read(./docs/archive/**)",
      "Read(./uv.lock)",
      "Read(./ui/pnpm-lock.yaml)"
    ]
  }

```

Для других инструментов — аналогичные файлы игнорирования. Плюс `.gitignore` для весов и логов.

### 9.7 Генератор карты проекта

```python
# tools/gen_map.py
"""Генерирует docs/ai/PROJECT_MAP.md из docstring-ов и публичных символов пакетов."""
import ast
import sys
from collections.abc import Iterator
from pathlib import Path

SRC = Path("src/vtuber")
OUT = Path("docs/ai/PROJECT_MAP.md")
SYMBOLS = (ast.ClassDef, ast.FunctionDef, ast.AsyncFunctionDef)


def _summary(node: ast.Module | ast.ClassDef | ast.FunctionDef | ast.AsyncFunctionDef) -> str:
    return (ast.get_docstring(node) or "—").partition("\n")[0]


def _entries(path: Path) -> Iterator[str]:
    for node in ast.parse(path.read_text(encoding="utf-8")).body:
        if isinstance(node, SYMBOLS) and not node.name.startswith("_"):
            yield f"- `{node.name}` — `{path.as_posix()}:{node.lineno}` — {_summary(node)}"


def render() -> str:
    lines = ["# PROJECT MAP", "", "> Автогенерация: `python tools/gen_map.py`. Не редактировать.", ""]
    for init in sorted(SRC.rglob("__init__.py")):
        package = init.parent
        lines += [f"## {package.as_posix()}", _summary(ast.parse(init.read_text(encoding="utf-8"))), ""]
        lines += [entry for module in sorted(package.glob("*.py")) for entry in _entries(module)]
        lines.append("")
    return "\n".join(lines)


def main() -> int:
    content = render()
    if "--check" in sys.argv:
        return int(OUT.read_text(encoding="utf-8") != content)
    OUT.write_text(content, encoding="utf-8")
    return 0


if __name__ == "__main__":
    raise SystemExit(main())
```

Результат выглядит так:

```markdown
## src/vtuber/application/pipeline
Конвейер ответа: LLM → разбор тегов → нарезка фраз → TTS.

- `SentenceChunker` — `src/vtuber/application/pipeline/chunker.py:12` — Режет поток текста на фразы для TTS.
- `ReplyPipeline` — `src/vtuber/application/pipeline/reply_pipeline.py:17` — Конвейер хода: стадии работают параллельно.
```

Аналогичный генератор для фронтенда (`tools/gen_map_ui.ts` на основе TypeScript Compiler API
или просто по экспортам) дописывает раздел `## ui/src/...` — на Этапе 5.

### 9.9 Когда контекст заканчивается

- Если сессия разрослась — завершить её по чек-листу финиша (даже если задача не доделана:
  в STATE.md пишется точное место остановки) и начать новую. Благодаря STATE.md новая сессия
  продолжит с того же места за пару минут.
- Признак неправильной нарезки: две сессии подряд не укладываются в контекст → задача делится
  в STAGE_X.md.

## 11. Тестирование, бенчмарки, оценка качества

### 11.1 Пирамида тестов

```text
            ┌────────────┐
            │  ручной    │  сценарии вех M1–M8 (чек-листы)
            ├────────────┤
            │  e2e       │  WebSocket-клиент ↔ ядро с фейками
          ┌─┴────────────┴─┐
          │  интеграционные │  реальные llama-server/TTS (@gpu, @slow)
        ┌─┴────────────────┴─┐
        │   контрактные       │  каждый адаптер × тест своего порта (LSP)
      ┌─┴────────────────────┴─┐
      │       модульные         │  domain, application, kernel — без GPU, мс на тест
      └─────────────────────────┘
```

### 11.2 Фейки (tests/fakes/)

- `FakeLLM(text, chunk_size, delay_ms)` — эмулирует стрим с задержкой; умеет «падать» на N-м
  токене.
- `FakeTTS(rtf)` — выдаёт тишину нужной длины с нужной скоростью.
- `RecordingSink` — записывает всё, что пришло, с отметками времени.
- `FakeClock` — управляемое время для тестов затухания, планировщика, дебаунса.

С фейками весь конвейер тестируется детерминированно: «первая фраза ушла в TTS раньше, чем LLM
закончил» — проверяемое утверждение.

### 11.3 Контрактные тесты (LSP на практике)

```python
# tests/contract/test_tts_contract.py
"""Любой адаптер TTSPort обязан пройти эти тесты."""
import asyncio

import pytest

from tests.contract.factories import tts_adapters
from vtuber.ports.tts import TTSPort


@pytest.fixture(params=tts_adapters(), ids=lambda factory: factory.__name__)
def tts(request: pytest.FixtureRequest) -> TTSPort:
    return request.param()


async def test_returns_pcm_in_declared_format(tts: TTSPort) -> None:
    chunks = [chunk async for chunk in tts.synthesize("Привет, как дела?")]
    assert chunks
    assert all(chunk.format == tts.audio_format for chunk in chunks)


async def test_cancellation_propagates(tts: TTSPort) -> None:
    async def consume() -> None:
        async for _ in tts.synthesize("Длинная фраза для проверки отмены синтеза речи."):
            await asyncio.sleep(0)

    task = asyncio.create_task(consume())
    await asyncio.sleep(0)
    task.cancel()
    with pytest.raises(asyncio.CancelledError):
        await task
```

Фабрика `tts_adapters()` возвращает фейк всегда, а реальные адаптеры — если доступны их модели
(иначе тест помечается как пропущенный с причиной).

### 11.4 Оценка качества ответов

`eval/qa_ru.jsonl`, одна строка — один кейс:

```json
{"id": "facts-001", "kind": "knowledge", "turns": ["Какая самая длинная река в Европе?"], "expect": {"any_of": ["Волга"]}}
{"id": "mem-003", "kind": "memory", "turns": ["Меня зовут Саша.", "<new_session>", "Как меня зовут?"], "expect": {"any_of": ["Саша"]}}
{"id": "honesty-002", "kind": "honesty", "turns": ["Что я ел вчера на ужин?"], "expect": {"refusal": true}}
{"id": "persona-005", "kind": "persona", "turns": ["Расскажи о себе"], "expect": {"max_sentences": 3, "no_markdown": true}}
```

- Категории: знания, память, честность («не знаю» вместо выдумки), следование персоне (длина,
  отсутствие разметки, теги), русский язык.
- Проверки: ключевые слова/регулярные выражения, структурные правила; для спорных — оценка более
  крупной локальной моделью-судьёй по рубрике (офлайн, не в горячем пути) + выборочная ручная
  проверка.
- `tools/eval_quality.py` выдаёт таблицу по категориям и сохраняет отчёт; результаты прогона
  прикладываются к ADR выбора модели и к PR, меняющим промпты/персону/память.

### 11.5 Бенчмарк задержек

- `bench/prompts_ru.jsonl` — 30–50 реплик: короткие («Привет!»), средние, длинные, с вопросами
  о памяти.
- Каждая реплика прогоняется N раз с прогретым кэшем и в «сценарии диалога» (последовательные
  ходы, как в жизни).
- Вывод: p50/p95/max по каждой метрике 3.2 и каждой строке бюджета 3.3, сравнение
  с `baseline.json`.

## 12. Риски и способы их снять

| Риск | Вероятность | Влияние | Как снимаем |
|---|---|---|---|
| Малая модель плохо говорит по-русски / выдумывает | высокая | высокое | Отбор по eval (Этап 2), RAG и честность (Этап 10), короткие ответы; готовность взять 12–14B ценой TPS |
| Не укладываемся в TTFA | средняя | высокое | Конвейер с первых этапов, замеры с Этапа 2, быстрый TTS на CPU, агрессивная первая фраза, заглушки-междометия |
| GPU не тянет LLM + TTS + STT | средняя | высокое | TTS/STT на CPU, VRAM-бюджет в ADR, меньшая квантизация |
| Несовместимость версий Live2D-библиотек | средняя | среднее | Фиксация версий, ADR, интерфейс AvatarRenderer позволяет сменить реализацию |
| Лицензионные ограничения (Live2D, голос) | средняя | среднее/высокое для монетизации | Проверка на Этапе 0, docs/licenses.md, альтернативные голоса |
| Расползание архитектуры | высокая без контроля | высокое | import-linter, лимиты сложности, ревью по чек-листу, ADR |
| ИИ-ассистент теряет контекст / ломает чужие модули | высокая без протокола | среднее | Сессионный протокол, scope в каждой сессии, карточки модулей, deny-правила |
| Барг-ин срабатывает от собственного голоса | средняя | среднее | Эхоподавление в захвате, порог длительности VAD |
| Изменения API llama.cpp | средняя | низкое/среднее | Всё специфичное — в одном адаптере; контрактные и интеграционные тесты; фиксация версии сервера |
| Блокировки event loop | средняя | высокое | R-34, asyncio debug-режим в тестах, профилирование на Этапе 9 |

## 13. Аппаратные требования

| Уровень | GPU | RAM | CPU | Что получится |
|---|---|---|---|---|
| Минимум | 8 ГБ VRAM (класса RTX 3060 8GB / 4060) | 16 ГБ | 6 ядер | 7–8B Q4, TTS на CPU, STT small на CPU; NFR выполнимы с короткими ответами |
| Эталон (рекомендуемо) | 12–16 ГБ VRAM (класса RTX 3060 12GB / 4070 / 4060 Ti 16GB) | 32 ГБ | 8 ядер | 8–14B Q4/Q5, черновая модель для speculative decoding, STT на GPU |

| Без GPU | — | 32 ГБ | 8+ ядер | 3–4B модели, заметно медленнее; только для разработки и тестов |

Диск: NVMe SSD (загрузка модели в 5–10 ГБ с HDD съест бюджет холодного старта).

Ориентиры скорости (проверяются на своём железе на Этапе 2): 8B Q4 на картах среднего класса —
порядка 40–80 токенов/с, на топовых — более 100. Этого с запасом хватает для непрерывной речи
(3.2): узкое место — TTFT и TTS первой фразы.

## 14. Глоссарий

| Термин | Значение |
|---|---|
| ADR | Architecture Decision Record — короткий документ об одном архитектурном решении |
| Barge-in | Перебивание: пользователь начинает говорить, витюбер замолкает |
| GGUF | Формат файлов моделей для llama.cpp, поддерживает квантизацию |
| KV-кэш | Сохранённые промежуточные вычисления внимания для уже обработанных токенов; позволяет не пересчитывать префикс |
| Prefill | Обработка входного промпта моделью до генерации первого токена |
| Speculative prefill | Обработка черновика промпта заранее, пока пользователь печатает/говорит |
| Speculative decoding | Ускорение генерации: маленькая модель предлагает токены, большая проверяет пачкой |
| Квантизация (Q4_K_M и т.п.) | Сжатие весов модели до 4–5 бит: меньше VRAM, быстрее, немного хуже качество |
| Липсинк | Синхронизация движения рта со звуком |
| Порт / адаптер | Интерфейс, которым ядро описывает потребность / реализация этого интерфейса для конкретной технологии |
| Корень композиции | Единственное место, где создаются и связываются все объекты приложения |
| RAG | Retrieval-Augmented Generation — поиск релевантных данных и добавление их в промпт |
| RTF | Real-Time Factor — время синтеза, делённое на длительность синтезированного звука |
| Sidecar | Вспомогательный процесс, запускаемый и управляемый основным приложением (Tauri) |
| Слот (llama.cpp) | Независимый поток обработки запросов со своим KV-кэшем |
| SSE | Server-Sent Events — потоковая передача ответа по HTTP |
| TTFT / TTFS / TTFA | Время до первого токена / первой фразы / первого звука |
| VAD | Voice Activity Detection — определение, говорит ли человек |
| Визема | Визуальная форма рта, соответствующая звуку речи |

## Итог

Проект реалистичен на потребительском железе, если с первого дня соблюдать три вещи:

1. **Скорость — это архитектура.** Стриминг, конвейер по фразам, стабильный префикс промпта
   и мгновенная отмена закладываются на Этапах 2–7, а не «оптимизируются потом». Всё измеряется.
2. **Дисциплина — автоматическая.** Правила, которые проверяет машина (линтер, типы, контракты
   импорта, лимиты сложности), не нарушаются. Остальное — чек-лист ревью с номерами правил.
3. **ИИ работает по карте.** STATE → этап → карта → карточка модуля → точечные строки. Каждая
   сессия маленькая, с явным scope, и заканчивается обновлением памяти проекта.

Первый практический шаг — Этап 0, сессия S-0.1.
