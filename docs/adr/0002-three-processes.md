# ADR-0002: Три процесса — UI, Ядро, LLM-сервер
- Статус: принято
- Дата: 2026-10-27

## Контекст
Нужны: лучший доступный рендер Live2D/VRM и точный анализ звука (веб-экосистема), экосистема
локального ИИ (Python), максимально быстрый инференс LLM (C++/CUDA). Падение модели не должно
ронять приложение. Каждый межпроцессный переход — сериализация и задержка (P1).

## Рассмотренные варианты
1. **Три процесса:** UI (Tauri 2 + Svelte) ↔ WebSocket ↔ Ядро (Python asyncio) ↔ HTTP/SSE ↔
   llama-server. Плюсы: каждый процесс на своём лучшем стеке; LLM-сервер заменяем
   (llama.cpp ↔ Ollama ↔ LM Studio ↔ vLLM) сменой адаптера; изоляция падений. Минусы: два
   межпроцессных перехода (на localhost — доли миллисекунды).
2. **LLM внутри Python** (llama-cpp-python и т.п.). Плюсы: на один переход меньше. Минусы:
   отставание биндингов от сервера (слоты, speculative decoding), падение модели роняет ядро,
   GIL и блокировки event loop.
3. **Микросервисы** (отдельные процессы для TTS, STT, памяти). Минусы: лишняя сериализация на
   каждом шаге горячего пути без выигрыша.
4. **Всё на Python (PySide6/Qt).** Минусы: тяжёлый Qt WebEngine, хуже инструменты веб-рендера
   аватара; см. `docs/stack.md`.

## Решение
Вариант 1. Tauri запускает ядро как sidecar-процесс (в разработке — отдельно). Ядро говорит
с llama-server по OpenAI-совместимому API со стримингом SSE. TTS/STT работают внутри процесса
ядра в потоках (`asyncio.to_thread`); тяжёлый GPU-TTS — в отдельном процессе (T-11).

## Последствия
- Протокол UI ↔ Ядро — единый источник схемы в `gateway/protocol.py` с генерацией TS-типов.
- Аудио идёт бинарными кадрами, без base64.
- Ядро не зависит от выбора UI: любой клиент протокола WebSocket работает.
- Упаковка (Этап 13) поставляет три артефакта: оболочку Tauri, sidecar ядра, llama-server.
