# ADR-0003: Звук воспроизводит UI, он же считает липсинк
- Статус: принято
- Дата: 2026-10-27

## Контекст
Рот модели должен двигаться синхронно с реально звучащим звуком (FR-05), без визуального
запаздывания; отмена должна давать тишину ≤ 100 мс (NFR-04). Текст генерируется быстрее, чем
произносится, поэтому синхронизировать рот по тексту нельзя.

## Рассмотренные варианты
1. **Воспроизведение и анализ в UI.** Ядро шлёт PCM бинарными кадрами; UI играет через
   AudioWorklet, AnalyserNode раз в кадр отдаёт RMS → сглаживание → `ParamMouthOpenY`. Плюсы:
   рот считается из того же буфера, что звучит, — синхронизация точная «бесплатно»; дешевле всего.
   Минусы: липсинк по громкости, а не по фонемам.
2. **Воспроизведение в ядре** (sounddevice и т.п.), параметры рта — сообщениями в UI. Минусы:
   рассинхрон из-за разных часов и задержки доставки; лишний трафик каждый кадр.
3. **Визем-липсинк по фонемам от TTS.** Плюсы: выразительнее. Минусы: не все движки отдают
   фонемы; сложнее; не нужен для MVP.

## Решение
Вариант 1. Визем-липсинк — опция Этапа 8 поверх того же плеера. Захват микрофона (Этап 11) тоже
в UI — ради встроенного эхоподавления браузерного движка.

## Последствия
- Формат звука объявляет `TTSPort.audio_format`; ресемплинг делает WebAudio.
- UI подтверждает воспроизведение (`audio.played`) — так измеряется настоящий TTFA.
- По `turn.cancelled` UI сбрасывает аудиобуфер — отмена до тишины не ждёт ядро.
