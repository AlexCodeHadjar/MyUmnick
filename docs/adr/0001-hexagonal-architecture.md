# ADR-0001: Гексагональная архитектура ядра (порты и адаптеры)
- Статус: принято
- Дата: 2026-10-27

## Контекст
Ядро соединяет LLM, TTS, STT, память и UI. Каждый из этих бэкендов будет заменяться: модели
выбираются бенчмарком (Этапы 2, 7), появляются плагины (Этап 12). Требования: замена бэкенда —
новый адаптер и строка в конфиге (NFR-09, FR-12); прикладной слой тестируется за миллисекунды без
GPU (NFR-08); проект большой и пишется сессиями ИИ — нужны жёсткие, проверяемые машиной границы.

## Рассмотренные варианты
1. **Порты и адаптеры + корень композиции.** Домен и сценарии зависят только от Protocol-портов;
   конкретика подставляется в `bootstrap`. Плюсы: заменяемость, тестируемость фейками, границы
   проверяет import-linter. Минусы: больше файлов и явной «проводки» в bootstrap.
2. **Готовый LLM-фреймворк (цепочки, агенты).** Плюсы: быстрый старт. Минусы: непрозрачные слои
   в горячем пути, лишняя задержка, сложно контролировать KV-кэш и отмену.
3. **Слоистое приложение без инверсии зависимостей.** Плюсы: проще в начале. Минусы: сценарии
   импортируют httpx/torch, тесты требуют GPU, замена бэкенда трогает бизнес-логику.

## Решение
Вариант 1. Слои: domain ← ports ← application ← adapters | gateway ← bootstrap; kernel (шина,
реестр, телеметрия, конфиг-база) не зависит ни от одного слоя. Порты — `typing.Protocol`
(структурная типизация). Реализации выбираются строкой конфига через `Registry[T]`; объекты
создаются только в `bootstrap/container.py`. Горячий путь — `asyncio.Queue` между стадиями,
управляющие события — `EventBus`.

## Последствия
- Контракты слоёв в `.importlinter` проверяются в pre-commit и CI; нарушение роняет сборку.
- Каждый порт получает контрактный тест, который проходят все его адаптеры (R-57).
- Свой тонкий слой работы с LLM (200–300 строк) вместо фреймворка — полный контроль над стримингом,
  кэшем и отменой.
- Открытый вопрос: публикация метрик из kernel без импорта domain — ADR в S-1.3.
- Подробности — `docs/architecture.md`.
