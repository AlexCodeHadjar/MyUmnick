## 1. Что это за проект

Локальный ИИ-витюбер / компаньон по имени **«Умник»** (персонаж Мика). Работает **полностью офлайн**:
- **Персонаж** справа, **чат** слева; есть отдельное окно персонажа и режим «Сопровождение» (персонаж
  гуляет поверх рабочего стола).
- **«Мозг»** — локальная LLM через `llama-server` (llama.cpp).
- **Голос** — TTS (Silero `xenia` по умолчанию, Piper `denis` запасной; OmniVoice — голос по образцу;
  Kokoro для английского). **Слух** — faster-whisper + Silero VAD, активация по имени «Умник».
- **Память** — e5 ONNX + sqlite-vec, плюс Obsidian-хранилище; чаты со своей памятью.
- Два издания: русское (основное) и английское (`--edition en`, ADR-0032).
- Мобильное приложение Android (`mobile/android/`) — «Карманный Умник» (Этап 24).

**Основной язык общения витюбера и документации — русский.**

**Целевое железо:** RTX 5070 Ti 16 ГБ VRAM, 32 ГБ RAM. ПК разработки в расчётах не учитывать.

### Приоритеты (строго по порядку)
1. **Скорость ответа** (TTFT, TTFA).
2. Правильность.
3. Расширяемость.
4. Внешний вид.

## 2. Архитектура в одной картинке

```text
UI (Tauri 2 + Svelte 5 + TS, ui/)
   │  WebSocket ws://127.0.0.1:8765 (JSON + бинарные аудиокадры)
Ядро (Python 3.12 asyncio, src/vtuber/)
   │  HTTP/SSE
llama-server (llama.cpp, GGUF, всё на GPU)
```

Три процесса (ADR-0002). Ядро — **гексагональная архитектура** (ADR-0001).

### Слои ядра (`src/vtuber/`) и разрешённые зависимости

| Слой | Что внутри | Может импортировать |
|---|---|---|
| `domain` | Неизменяемые сущности: Message, Turn, Persona, Emotion, AudioChunk, доменные ошибки | только stdlib |
| `ports` | `typing.Protocol`-интерфейсы: LLMPort, TTSPort, STTPort, EmbedderPort, MemoryStorePort, ReplySink, ClockPort | domain |
| `kernel` | EventBus, Registry, телеметрия, базовый конфиг, логирование | stdlib, structlog, pydantic, domain (ADR-0005) |
| `application` | ConversationService, ReplyPipeline, PromptBuilder, SentenceChunker, StreamParser, MemoryService, IdleScheduler… | ports, domain, kernel |
| `adapters` | LlamaCppLLM, SileroTTS, PiperTTS, FasterWhisperSTT, SqliteVecStore… | ports, domain, kernel, внешние SDK |
| `gateway` | WebSocket-сервер, протокол, кодеки, WsReplySink | application, ports, domain, kernel |
| `bootstrap` | Корень композиции: container, main, AppConfig, загрузка плагинов | всё |

Правило направления: `domain ← ports ← application ← adapters | gateway ← bootstrap`.
Контракты проверяет **import-linter** (`.importlinter`). Адаптеры не импортируют друг друга,
application и gateway.

## 4. Git и репозиторий

- Remote: `origin` → `https://github.com/AlexCodeHadjar/MyUmnick.git`, основная ветка **`main`**.
- **Коммиты — Conventional Commits (R-68):** `feat(tts): add piper adapter`, `fix(pipeline): …`,
  `perf(llm): …`, `docs: …`, `refactor: …`, `test: …`, `chore: …`. Области (scope) — имя модуля/фичи:
  `companion`, `ui`, `pipeline`, `tts`, `memory` и т. д. Сообщения — по-английски, коротко, по делу.
- Формально (R-69/R-70): одна задача — одна ветка — один PR ≤ ~400 строк, в `main` через PR с
  зелёным CI. **Фактически** пользователь разрешил работать прямо в `main`, идти по сессиям без
  подтверждения, коммитить и пушить сразу.
- Документация обновляется **в том же коммите**, что и код (R-71).
- Не коммитится (`.gitignore`): `models/`, `logs/`, `data/` (кроме `tests/data/`), `config/user.toml`,
  `node_modules/`, `ui/dist/`, `ui/src-tauri/target/`, `ui/src-tauri/gen/`,
  `bench/results/tts_samples/`, кэши инструментов.
- Перед коммитом: `uv run pre-commit run --all-files` должен быть зелёным. Хуки не обходить
  (`--no-verify` запрещён).

## 6. Протокол рабочей сессии (обязателен)

Полностью — `docs/ai/WORKFLOW.md`. Кратко:

**Старт**
1. `docs/ai/STATE.md` → номер текущей сессии S-X.Y.
2. `docs/stages/STAGE_XX.md` → цель, scope (список файлов), критерии готовности.
3. Найти модули из scope в `PROJECT_MAP.md` поиском.
4. Прочитать их карточки (`README.md` пакета).
5. Составить план 3–7 шагов и явно перечислить изменяемые файлы.
   **Нужен файл вне scope — остановиться и объяснить.**

**Работа**
- Сначала тест (или контрактный тест для адаптера), потом код. Баг → сначала падающий тест (R-59).
- Читать точечно: поиск символа → нужный диапазон строк.
- Гонять релевантные тесты, полный прогон — в конце.
- Не «улучшать попутно» код вне scope; замеченное записать в «Открытые проблемы» STATE.md.
- Одна сессия = одна задача = 1–2 модуля, ориентир ≤ 6 файлов и ≤ 400 строк диффа.
  Порядок внутри этапа: порт → фейк → контрактный тест → адаптер → сценарий → интеграция.

**Финиш (чек-лист)**
- [ ] `uv run pre-commit run --all-files` и `uv run pytest --cov` — зелёные (для UI — `pnpm test`, `pnpm check`, `pnpm lint`).
- [ ] Обновлены карточки изменённых модулей (`<пакет>/README.md`).
- [ ] `uv run python -m tools.gen_map` (+ `tools/gen_protocol.py`, если менялся протокол).
- [ ] Журнал сессии `docs/ai/sessions/YYYY-MM-DD_S-X.Y.md` (шаблон `docs/templates/SESSION_LOG.md`).
- [ ] **Перезаписан** (не дописан) `docs/ai/STATE.md`: следующая сессия, открытые проблемы.
- [ ] Галочки и статус сессии в `STAGE_XX.md`.
- [ ] Коммит(ы) по Conventional Commits, push.

Контекст кончается — завершить сессию по чек-листу, записав в STATE.md точное место остановки.

## 7. Правила кода (сжато; полный текст — `docs/rules/code-rules.md`)

**Главный принцип:** каждая строка необходима, каждое имя понятно. «Профессионально» = минимально и
очевидно, а не «умно». Расширение — добавлением, а не правкой.

### A. Архитектура
- **R-01** Зависимости слоёв строго по таблице (раздел 2). Домен не импортирует ничего из проекта.
- **R-02** Адаптеры не импортируют друг друга, application и gateway.
- **R-03** Адаптеры создаются **только в bootstrap**; везде — внедрение через конструктор.
- **R-04** Нет изменяемого глобального состояния. Модульные константы — `Final`, `frozenset`, `tuple`.
- **R-05** Один модуль — одна ответственность (нужно слово «и» в описании → делить).
- **R-06** Публичный API пакета — только `__all__` в `__init__.py`; импорт из чужого пакета в обход `__init__` запрещён.
- **R-07** Новая реализация порта = новый файл адаптера + строка в реестре/конфиге. Иначе нужен ADR.
- **R-08** Горячий путь (LLM → парсер → нарезка → TTS → sink) — через `asyncio.Queue`, **не через шину событий**, без синхронного I/O.

### B. Размер и сложность (проверяется машиной)
| Правило | Предел |
|---|---|
| R-09 строка | 100 символов |
| R-10 файл | **250 строк кода** (без пустых/комментариев/docstring; ориентир 200) — `tools/check_file_length.py` |
| R-11 инструкций в функции | **20** |
| R-12 цикломатическая сложность | **8** |
| R-13 аргументов | **4** (без self); больше — dataclass параметров |
| R-14 вложенность | 3 уровня |
| R-15 публичных методов в классе | 7 |
| R-16 return в функции | 4 |

### C. Типизация
- **R-17** `mypy --strict` без ошибок, всё аннотировано.
- **R-18** `Any` запрещён (исключение — граница с нетипизированной библиотекой в адаптере с `# boundary:`).
- **R-19** `# type: ignore[код]` — только с кодом и причиной.
- **R-20** Интерфейсы — `typing.Protocol`.
- **R-21** Данные — `@dataclass(frozen=True, slots=True)`; изменяемые — только осознанно, со `slots=True`.
- **R-22** Enum/Literal вместо строк-кодов; dataclass/TypedDict вместо dict с фиксированными ключами.

### D. Лаконичность
DRY с 3+ строк (R-23); без тривиальных геттеров (R-24); `return x > 0` вместо if/else (R-25);
нет else после return (R-26); включения для коллекций (R-27); stdlib прежде самописного (R-28);
нет мёртвого/закомментированного кода и «на будущее» (R-29); не перепроверять гарантированное типами (R-30);
**нет магических чисел — в конфиг или именованную константу (R-31)**; нет пустых обёрток (R-32);
нет «хитрых» однострочников — моржа в включениях, вложенных тернарников (R-33).

### E. Асинхронность и производительность
- **R-34** В корутинах нет блокирующих вызовов; CPU-работа — `asyncio.to_thread` / пул процессов.
- **R-35** Параллельные подзадачи — только `asyncio.TaskGroup`; «висячие» `create_task` запрещены.
- **R-36** Каждый внешний вызов — с тайм-аутом.
- **R-37** Ресурсы — только через `async with` / `with`.
- **R-38** `asyncio.CancelledError` **никогда не подавляется** (перехват только для очистки + `raise`).
- **R-39** Изменение горячего пути — **с замером до/после**.
- **R-40** Тяжёлые объекты (модели, HTTP-сессии) создаются один раз при старте.
- **R-41** В горячем пути без лишних копий: аудио — bytes/memoryview, без `+=` на больших строках.

### F. Ошибки
- **R-42** Голые `except:` / `except Exception:` — только на верхних границах (обработчик хода, WS-сессия, фоновая задача), с логом и `turn_id`.
- **R-43** Чужие исключения → доменные в адаптере: `raise LLMUnavailable(...) from exc`.
- **R-44** Ошибки не возвращаются кодами/None.
- **R-45** Сообщение ошибки говорит, что делать («LLM-сервер не отвечает на 127.0.0.1:8080 — запущен ли scripts/start_llm?»).

### G. Именование
PEP 8 (R-46); без сокращений кроме llm, tts, stt, cfg, id; булевы `is_/has_/should_` (R-47);
функция — глагол, класс — существительное, порт — `…Port`, адаптер — `<Движок><Порт>` (`SileroTTS`) (R-48);
абсолютные отсортированные импорты, без `*` (R-49); формат — `ruff format` (R-50).

### H. Комментарии

### SOLID — как это выглядит здесь
- **S:** `ReplyPipeline` только соединяет стадии; не режет текст (`SentenceChunker`), не разбирает теги (`StreamParser`), не знает о WebSocket (`ReplySink`).
- **O:** новый TTS = новый файл в `adapters/tts/` + `add("name", Adapter)` в реестре bootstrap. Никаких `if cfg.tts.backend == "silero" … elif …` вне реестра.
- **L:** любой адаптер порта взаимозаменяем — закреплено контрактными тестами. Никаких `isinstance(tts, PiperTTS)` в конвейере.
- **I:** маленькие порты (`EmbedderPort` отдельно от `MemoryStorePort`).
- **D:** application зависит от `LLMPort`, а не от `LlamaCppLLM`.

## 8. Скорость и оптимизация (полностью — `docs/performance.md`)

### Метрики
TTFT (до первого токена), TTFS (до первой фразы для TTS), **TTFA (до первого звука — главная)**,
TPS, RTF (синтез/длительность, должен быть < 0.3), Gap (паузы между фразами ≈ 0),
Cancel latency (от «Стоп» до тишины), E2E.

### Бюджет TTFA ≤ 800 мс (контракт; регрессия p95 > 15 % — провал)
| Стадия | Бюджет |
|---|---|
| UI → Ядро (WS) | ≤ 3 мс |
| Валидация и маршрутизация | ≤ 2 мс |
| Гейт RAG + поиск в памяти | ≤ 40 мс (0, если не нужен) |
| Сборка промпта | ≤ 5 мс |
| Prefill новых токенов | ≤ 100 мс |
| Первая фраза | ≤ 300 мс |
| TTS первой фразы | ≤ 250 мс |
| Ядро → UI (аудиокадр) | ≤ 5 мс |
| Буфер WebAudio | ≤ 40 мс |
| **Итого** | **≈ 750 мс** |

### Техники T-01…T-17 (ссылаться на них в комментариях)
- **T-01** Стриминг везде — ни одна стадия не ждёт полного результата предыдущей.
- **T-02** Конвейер по фразам: первая фраза режется рано (по запятой после 4 слов), следующие — длиннее (~10 слов или точка).
- **T-03** Стабильный префикс промпта ради KV-кэша: персона → резюме → история (только дописывается) → динамический блок → реплика.
- **T-04** Блочное усечение истории (не по одному сообщению — иначе ломается KV-кэш).
- **T-05** Speculative prefill во время набора (дебаунс ~300 мс).
- **T-06** Прогрев моделей при старте.
- **T-07** Короткие ответы (1–3 предложения) по умолчанию.
- **T-08** Без reasoning-режима в горячем пути.
- **T-09** Speculative decoding (сейчас draft-модель выключена — ADR-0030).
- **T-10** Квантизация GGUF Q4_K_M/Q5_K_M, все слои на GPU.
- **T-11** Разведение ресурсов: LLM на GPU, быстрый TTS на CPU.
- **T-12** Гейтинг поиска по памяти (`retrieval_gate.py`).
- **T-13** Фоновые задачи (суммаризация, факты, индексация) — только в простое.
- **T-14** Мгновенная отмена хода целиком (генерация, TTS, звук).
- **T-15** Тонкий горячий путь — `asyncio.Queue` напрямую, без шины.
- **T-16** Батчинг отрисовки в UI по rAF.
- **T-17** Воспринимаемая скорость: аватар реагирует в кадре отправки («думаю», кивок, междометия «Хм…» через 1000 мс без звука).

Замер: `uv run python -m tools.bench_latency`, `tools.bench_voice`, `tools.perf_gate`.
Реальные цифры на 5070 Ti — `docs/perf/gpu-run-2026-11-02.md`, сырьё — `bench/results/remote/`.

в спутнике. Порядок работы по каждой задаче:

### Общие ограничения
- **Всё — только визуал.** Спутник ничего не нажимает, не открывает, не перемещает и не удаляет файлы,
  не читает их содержимое. Удаление «в корзину», «спрятал в карман» — нарисованное действие.
- **Приватность:** клавиатуру не перехватывать и клавиши не хранить (как в `typing.rs`); буфер обмена —
  только факт копирования, без чтения текста (или максимум несколько первых символов только для показа, не сохраняя).
- **Не мешать работе:** не перекрывать активное поле ввода, не лезть под курсор во время работы, учитывать
  режим «Спокойнее» (ADR-0052) и полный экран (фильм/игра — не активничать).
- **Редкость:** у каждого поведения — шанс и пауза перехода (cooldown) в настройках (`settings.ts`), а не
  магические числа в коде (R-31). Ничего не должно повторяться так часто, чтобы надоесть.
- **Производительность:** опрос системы — в Rust-потоке спутника редко и дёшево; анимации — в цикле
  отрисовки вне реактивности Svelte (R-66); спутник не должен заметно грузить CPU в простое.
- Строки — в оба i18n-файла (`ru.ts`, `en.ts`).

### A. Взаимодействие с мышью
- **Поглаживание:** пользователь водит курсором по персонажу туда-сюда — он довольно жмурится
  (поза «жмурится», можно сердечки/искорки). Узнавать по нескольким сменам направления курсора над
  прямоугольником персонажа за короткое время.
- **Тянется к курсору:** курсор приближается — персонаж тянется к нему и следит, как кошка за лазерной
  указкой (взгляд, наклон, может подпрыгнуть/хлопнуть лапкой). Не во время набора текста и не всегда.

### B. Окна и экран
- **Выглядывает из-за края окна**, как из-за угла: прячется за край окна, видна только голова/часть тела.
- **Стучит изнутри по стеклу экрана:** подходит к «стеклу», стучит, на экране — небольшой эффект удара/кругов.

### C. Файлы и работа (только визуал)
- **Скачивается файл:** тащит на спине коробку, шатается тем сильнее, чем больше файл. Сигнал — новый
  растущий файл в папке «Загрузки» (только имя и размер).
- **Сохранение (Ctrl+S):** ставит штамп «Сохранено!». Сигнал — без перехвата клавиш: например, изменение
  заголовка окна (пропала `*`) или изменение файла недавних; подобрать надёжный способ.

### D. Характер и жизнь
- **Мини-хобби, когда скучно:** рисует, читает крошечную книжку, жонглирует иконками.
- **Падения и спотыкания** с шансом 1–2 %.
- **Питомец у питомца:** маленький жук или пиксель, за которым он иногда гоняется (своя простая логика движения).

### 1. «Находка»
Подходит к краю окна или к панели задач, «достаёт» файл — **иконка и имя настоящего файла из «Недавних»**
(только для показа) — и вертит его в руках: подносит к глазам, трясёт, нюхает. Один из трёх финалов:
- 🎒 прячет в карман, и карман потом заметно оттопыривается;
- 🔙 аккуратно кладёт обратно;
- 🗑 бросает в нарисованную корзину и отряхивает руки.

### 2. Инвентарь в кармане
Всё «спрятанное» хранится в маленьком инвентаре (хранится между запусками, локально). Клик по карману —
показать содержимое. Иногда сам достаёт вещь: «Помнишь этот скриншот? Я его храню». Это наглядная
долговременная память персонажа. Ограничить размер инвентаря; дать очистить.

### 3. Реакции на действия пользователя
- **Скопировал текст** — «ловит» его и прижимает к груди, как бумажку.
- **Сделал скриншот** — пугается вспышки и закрывает глаза.
- **Закрыл окно** — машет ему вслед.
- **Свернул всё (Win+D)** — его сдувает ветром.

### 9. Строит что-то со временем
За день работы постепенно строит в углу экрана домик или кучку из «найденных» файлов: чем дольше работа,
тем больше постройка — видимый показатель «мы сегодня много сделали». Есть кнопка сброса (в меню спутника).
Прогресс сохраняется в течение дня; угол не должен перекрывать важное (панель задач, значки).

### 10. Пишет записки
Иногда оставляет на экране стикер-записку от себя («Не забудь попить воды», «Ты третий час в этом файле»).
Записка висит, пока пользователь её не смахнёт; тогда он подбегает и забирает её обратно. Записки — редко,
текст — из набора фраз (`phrases`) с подстановкой фактов (время в окне, длительность работы).

### Результат по каждой задаче
Работает вживую в окне Tauri, есть тесты на логику выбора/сигнала, обновлены `companion/README.md` и
`docs/character/` (какие кадры нужны), STATE.md и журнал сессии; коммит `feat(companion): …`.

### 14.2. Требования к каждому кадру (FRAMES.md §2)
| Что | Позы тела | Мордашка `head_*` |
|---|---|---|

### 14.3. Как генерировать (FRAMES.md §3–§4)
1. **Одна группа кадров — один новый чат** (в длинном чате генератор «плывёт»).
2. Приложить `character-reference.png` + базовую позу группы (например, `stand.png`).
3. Вступление:
   ```
   The attached images are the exact reference for one character: a small hooded figure with a dark-blue
   hood and cloak, a cream mask with two black oval eyes, blue flame horns, blue flame tongues along the
   cloak hem, dark legs and small boots with buckles. Keep the design, colors, line style, shading and
   proportions identical in every image I ask for next. Every image is a clean cut-out on a fully
   transparent background. Do not reply with text, only with images.
   ```
4. **Один кадр — одно сообщение**: описание позы (вправо, 3/4, где опора, «Canvas 1024x1536, vertical») +
   обязательный хвост:
   ```
   Output a clean cut-out: a fully transparent background (alpha 0) everywhere outside the character —
   no glow halo, no smoke, no shadow, no dark aura, no vignette, no outline, no background color. The blue
   flames keep their own light but do not spill onto the background. No letters, no "z", no text, no
   symbols. Same character scale as the attached reference: the cream mask is about 184 px tall on a
   1024x1536 canvas. PNG.
   ```
   Кадры цикла: «Using the previous image as the reference, draw frame N of M of a looping …; the head and
   body stay in place, only … moves».
5. Брак — не править в том же чате, а попросить заново со ссылкой на требования.

### 14.4. Подгонка и подключение в программу
1. Привести группу к холсту **одним преобразованием на группу**: масштаб — по высоте белой маски к `stand`,
   опора — в точку из таблицы (ступни — на линию `stand`). Так цикл не дрожит.
2. Экспорт: **WebP, качество 90, высота 768** → `ui/public/characters/default/`.
3. Добавить имена в `index.json`; новую позу — в тип `Pose`, `ANCHORS`, при цикле — `LOOP_FPS` (`look/pack.ts`).
4. Записать в `docs/character/` (новый `FRAMES-5.md`): какие кадры, промпты, масштабы, исключения.
5. Подгонка делалась одноразовым скриптом на Pillow — Pillow **не** зависимость проекта, скрипт в репозиторий не класть.

### 14.5. Мелкие предметы и эффекты
Не всё нужно рисовать в кадре персонажа. Жук/пиксель-питомец, штамп «Сохранено!», стикер-записка, корзина,
коробка-«загрузка», ветер, вспышка скриншота, круги от стука по стеклу, домик из файлов, иконки «находок»
(настоящие иконки берутся из системы) — можно рисовать **отдельными спрайтами или кодом** (canvas/CSS) поверх
слоя спутника. Отдельные спрайты — тоже PNG с прозрачным фоном, в стиле персонажа (контур, голубой огонь,
тёмно-синий), класть рядом с пакетом в отдельную подпапку и описывать в `docs/character/`.
