# S-7.4 — Адаптер Piper · 2026-10-28

## Цель
`PiperTTS` с тем же контрактом; RTF < 0.3 на `bench/prompts_ru.jsonl`.

## Сделано
- ADR-0013: `piper-tts` 1.8.0 (OHF-Voice/piper1-gpl, GPL-3.0-or-later; onnxruntime 1.31,
  espeak-ng внутри) — необязательная группа `piper`; голос `ru_RU-denis-medium` (CC0) — с
  `huggingface.co/rhasspy/piper-voices`: `.onnx` 63 201 294 байт + `.onnx.json` 4 823 байт в
  `models/tts/piper/` (вне git).
- `adapters/tts/piper.py`: `PiperConfig` (`[tts.piper]`: `model_path`, `sample_rate` — сверяется
  с голосом, `length_scale`, `chunk_ms`), `PiperTTS` — загрузка и прогрев в `async with`, синтез
  в потоке под блокировкой, склейка фрагментов по предложениям и нарезка по `chunk_ms`, уступка
  цикла между фрагментами; ошибки onnxruntime (свои pybind-исключения) → `TTSUnavailable` /
  `GenerationFailed`. Пакет `piper` импортируется только при загрузке голоса.
- Silero: прогрев при загрузке (T-06) — как у Piper.
- Контракт: случай `piper` (`-m slow`, пропуск без голоса). Юнит-тесты Piper с фейковым голосом
  (8); тесты Silero учитывают вызов прогрева.
- Карточка `adapters/tts`, `docs/licenses.md`, `docs/stack.md`, README (загрузка голоса),
  STAGE_07, STATE.

## Решения
- `piper-tts`, а не свой вызов ONNX: фонемы espeak-ng пришлось бы собирать самим; GPL не
  срабатывает — приложение не распространяется (ADR-0011, ADR-0013).
- Частота голоса в конфиге, а не из `.onnx.json` на лету: формат известен до загрузки (конвейер,
  UI), расхождение с голосом — `TTSUnavailable` с подсказкой.
- Фраза синтезируется целиком, без отдачи по предложениям: нарезка (S-7.2) и так подаёт короткие
  фразы; потоковая отдача — если Piper станет основным (STATE, P3).
- **Отступление от scope:** секция `[tts.piper]` в `config/default.toml` не добавлена — корень
  конфига запрещает лишние ключи, нужна секция `tts` в `AppConfig` (bootstrap) с выбором
  движка; это подключение TTS — S-7.5, туда же `[tts.silero]` и `[pipeline.chunker]`.

  прогревает модель).
