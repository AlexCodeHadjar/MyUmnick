# S-4.2 — WebSocket-сервер, WsReplySink, e2e · 2026-10-27

## Цель
WebSocket-сервер (один клиент), маршрутизация в ConversationService, события шины → клиенту,
`WsReplySink`; e2e с FakeLLM; задержка «дельта → кадр у клиента» ≤ 3 мс p95.

## Сделано
- ADR-0008: websockets (17.3) для шлюза; orjson не нужен — JSON делает pydantic-core.
- `gateway/sink.py`: `WsReplySink` — текст → `chat.delta`, эмоция → `avatar.emotion`, номер хода —
  из `kernel.current_turn()`; вызов вне хода — `TurnStateError`.
- `gateway/server.py`: `GatewayServer` (async-контекст, `serve_forever`, `send`, `port`),
  `GatewayConfig` (`[gateway]`); один клиент — новое подключение вытесняет старое (4000);
  отключение посреди хода → `cancel(USER_STOP)`; битое/бинарное сообщение → `error bad_message`;
  подписка на `TurnStarted/Finished/Cancelled`, `MetricRecorded`, `BackendStatusChanged`;
  последний статус бэкенда — при подключении.
- `bootstrap/main.py`: режимы `chat` (по умолчанию) и `serve`; прогрев со статусом LLM
  `loading → ready | failed`; `serve` поднимает шлюз до прогрева и живёт, пока открыт stdin
  (sidecar Tauri умирает вместе с родителем); `Console` читает из `LineSource` (только
  `readline`, ISP).
- **Исправлен баг логирования**: кэш логгеров structlog привязывал логгеры модулей к первому
  потоку — после закрытия файла они падали с «I/O operation on closed file» (нашли тесты, когда
  `main` запускался несколько раз в одном процессе). Кэш выключен; `kernel.logging_to` сбрасывает
  настройку раньше, чем владелец закрывает файл. Регрессионный тест.
- Тесты: `tests/integration/test_ws_server.py` (7, включая задержку p95 ≤ 3 мс),
  `tests/integration/test_serve_app.py` (2: шлюз + ход + выход по stdin; LLM недоступна —
  шлюз живёт со статусом `failed`), `tests/unit/gateway/test_sink_and_server.py` (3);
  `tests/fakes/conversation.py` — сборка сервиса на фейках для тестов.
- Карточки gateway, bootstrap, kernel; `docs/stack.md`, `AGENTS.md`; STAGE_04, STATE.

## Решения
- Номер хода — из contextvar: порт `ReplySink` не меняется ради одного получателя.
- `done` в `WsReplySink` ничего не шлёт — конец хода приходит `turn.finished` из шины (один
  источник правды о завершении).
- Отключение клиента отменяет ход — GPU не работает впустую (T-14).
- `serve` не падает при недоступной LLM: UI показывает `failed`, ходы получают понятную ошибку.
- Выход `serve` по концу stdin — стандартный приём для sidecar-процессов.
