# Скорость — главный приоритет

Источник: мастер-план v1, раздел 3. Техники T-NN упоминаются в коде и документах — их смысл
только здесь. Изменения — через ADR.

## Анатомия задержки

Наивная (последовательная) схема:

```text
Пользователь нажал Enter
│
├─ сборка промпта ............ 5 мс
├─ prefill LLM (весь контекст) 400–1500 мс   ← пересчитывается каждый раз
├─ генерация всего ответа .... 1500–4000 мс  ← ждём конец
├─ синтез всего ответа ....... 800–3000 мс   ← ждём конец
└─ начало звука .............. ИТОГО 3–8 секунд  ✗
```

Целевая (конвейерная) схема:

```text
Enter ─┬─ аватар: анимация «думаю» ............................ ~16 мс (1 кадр)
       ├─ сборка промпта (префикс уже в KV-кэше) .............. ≤ 5 мс
       ├─ prefill только новых токенов ......................... 30–100 мс
       ├─ ПЕРВЫЙ ТОКЕН на экране (TTFT) ........................ ≤ 250 мс
       ├─ первая фраза готова (4–8 слов) ....................... +150–300 мс
       ├─ TTS первой фразы ..................................... +100–250 мс
       └─ ПЕРВЫЙ ЗВУК (TTFA) ................................... ≤ 800 мс  ✓
             │
             └─ пока звучит фраза 1: LLM пишет фразу 2, TTS синтезирует её
                → звук идёт без пауз
```

Задержки не складываются, а перекрываются: пользователь ждёт только «голову» конвейера.

## Метрики

| Метрика | Определение | Зачем |
|---|---|---|
| TTFT | От отправки сообщения до первого видимого токена | «Она меня услышала» |
| TTFS | До первой готовой фразы для TTS | Правильно ли режется текст |
| TTFA | До первого сэмпла звука в динамике | Главная метрика «живости» |
| TPS | Токенов в секунду при генерации | Хватает ли скорости, чтобы звук не прерывался |
| RTF | Время синтеза / длительность звука | Должен быть < 0.3, иначе голос «заикается» |
| Gap | Паузы между фразами при воспроизведении | ≈ 0, кроме естественных |
| Cancel latency | От «Стоп» до тишины и остановки генерации | NFR-04 |
| E2E | До конца ответа | Вторична, но отслеживается |

Условие непрерывной речи: генерация быстрее произнесения. Русская речь — примерно 2.5–3.5 ток/с
на слух, поэтому даже 25–30 ток/с дают запас ×8. Узкое место — не TPS, а TTFT и TTS первой фразы.

## Бюджет задержки (TTFA ≤ 800 мс)

| Стадия | Бюджет | Кто отвечает |
|---|---|---|
| UI → Ядро (WebSocket, localhost) | ≤ 3 мс | gateway |
| Валидация и маршрутизация | ≤ 2 мс | application/conversation |
| Решение «нужен ли RAG» + поиск | ≤ 40 мс (0 мс, если не нужен) | application/memory |
| Сборка промпта | ≤ 5 мс | application/prompting |
| Prefill новых токенов (префикс в кэше) | ≤ 100 мс | LLM-сервер |
| Генерация первой фразы | ≤ 300 мс | LLM-сервер + SentenceChunker |
| TTS первой фразы | ≤ 250 мс | adapters/tts |
| Ядро → UI (бинарный аудиокадр) | ≤ 5 мс | gateway |
| Буфер воспроизведения WebAudio | ≤ 40 мс | ui/features/audio |
| **Итого** | **≈ 750 мс** | |

Бюджет — контракт: бенчмарк Этапа 9 проверяет каждую строку; регрессия p95 > 15 % — провал.

## Техники ускорения

| ID | Техника | Этап |
|---|---|---|
| T-01 | Стриминг везде | 2–7 |
| T-02 | Конвейер по фразам с «агрессивной» первой фразой | 7 |
| T-03 | Стабильный префикс промпта → KV-кэш | 3 |
| T-04 | Блочное усечение истории | 3 |
| T-05 | Speculative prefill во время набора | 9 |
| T-06 | Прогрев при старте | 2 |
| T-07 | Короткие ответы по умолчанию | 3 |
| T-08 | Без reasoning-режима в горячем пути | 2 |
| T-09 | Speculative decoding | 9 |
| T-10 | Квантизация и полная выгрузка на GPU | 2 |
| T-11 | Разведение ресурсов GPU/CPU | 7, 9 |
| T-12 | Гейтинг поиска по памяти | 10 |
| T-13 | Фоновые задачи только в простое | 10 |
| T-14 | Мгновенная отмена | 3 |
| T-15 | Тонкий горячий путь | 1, 3 |
| T-16 | Батчинг отрисовки в UI | 5 |
| T-17 | Воспринимаемая скорость | 6, 8 |

**⏱ T-01. Стриминг везде.** LLM отдаёт токены потоком (SSE), ядро сразу пересылает их в UI,
UI отрисовывает. Ни одна стадия не ждёт полного результата предыдущей.

**⏱ T-02. Конвейер по фразам с «агрессивной» первой фразой.** Поток токенов режется на фразы
(`SentenceChunker`), каждая сразу уходит в TTS. Первая фраза отрезается раньше — по запятой уже
после 4 слов, чтобы звук начался быстрее. Последующие — длиннее (по точке или по запятой после
~10 слов): интонация естественнее. Первая фраза из 1–2 слов звучит неестественно, поэтому
минимум 4, а не 1.

**⏱ T-03. Стабильный префикс промпта.** llama.cpp хранит KV-кэш предыдущего запроса
и пересчитывает только отличающийся «хвост». Промпт строится «от неизменного к изменчивому»:

```text
[системный промпт персоны]            ← не меняется никогда за сессию
[сжатое резюме старой части диалога]  ← меняется редко (см. T-04)
[история последних N ходов]           ← только дописывается в конец
[динамический блок: время, найденные факты]  ← прямо перед репликой
[реплика пользователя]
```

Ошибка, убивающая кэш: текущее время или результаты поиска в системном промпте. Префикс меняется
каждый ход — prefill всего контекста повторяется (сотни миллисекунд).

**⏱ T-04. Блочное усечение истории.** Историю нельзя сдвигать «по одному сообщению» — это меняет
префикс каждый ход. При достижении лимита отрезается большой блок (например, старшая половина),
заменяется резюме, дальше снова только дописывание. Кэш инвалидируется раз в десятки ходов.

**⏱ T-05. Speculative prefill.** Пока пользователь печатает, UI с дебаунсом (~300 мс) шлёт
`input.typing`. Ядро отправляет в LLM-сервер прогрев кэша (prefill без генерации). К нажатию Enter
большая часть промпта уже в KV-кэше. Для голоса — то же по промежуточным гипотезам STT.

**⏱ T-06. Прогрев при старте.** После загрузки модели — холостой запрос с системным промптом
персоны: первый ответ не платит за холодный старт CUDA-ядер и prefill системного промпта. Для TTS —
синтез короткой фразы.

**⏱ T-07. Короткие ответы.** Персона отвечает 1–3 предложениями, если не просят подробностей;
`max_tokens` ограничен. Это и скорость, и естественность.

**⏱ T-08. Без «размышлений».** Reasoning-режим модели в диалоге выключен: сотни невидимых токенов
до первого видимого. Включается точечно для сложных вопросов (маршрутизация, Этап 10).

**⏱ T-09. Speculative decoding.** Маленькая черновая модель того же семейства ускоряет генерацию
в 1.3–2×. Включается флагом, только если бенчмарк показывает выигрыш.

**⏱ T-10. Квантизация и полная выгрузка на GPU.** GGUF Q4_K_M / Q5_K_M, все слои на GPU
(`-ngl 99`), Flash Attention, контекст не больше необходимого (8–16 тыс. токенов): большой
контекст съедает VRAM и замедляет prefill.

**⏱ T-11. Разведение ресурсов.** LLM — на GPU. Быстрый TTS (Silero/Piper) — на CPU и не
конкурирует за видеокарту. Тяжёлый TTS на GPU — в отдельном процессе, его VRAM — в бюджете заранее.

**⏱ T-12. Гейтинг поиска по памяти.** Поиск выполняется только если нужен (эвристика или лёгкий
классификатор: вопрос о прошлом, о пользователе, «помнишь…»). Эмбеддинг реплики можно посчитать
во время набора (вместе с T-05).

**⏱ T-13. Фон — только в простое.** Суммаризация, извлечение фактов, индексация — фоновые задачи;
запускаются в простое и отменяются сразу, как приходит новая реплика.

**⏱ T-14. Мгновенная отмена.** Новое сообщение или «Стоп» отменяет ход целиком: генерацию
(закрытием HTTP-потока — llama.cpp прекращает работу), синтез, воспроизведение. Иначе следующий
ответ ждёт, пока GPU доделает ненужный.

**⏱ T-15. Тонкий горячий путь.** Токены и аудио идут через `asyncio.Queue` напрямую между
стадиями, а не через шину событий. Сериализация — orjson. Логирование на каждый токен — только
DEBUG, выключено по умолчанию.

**⏱ T-16. Батчинг отрисовки в UI.** UI копит токены и применяет их раз в кадр
(`requestAnimationFrame`). Длинная история чата — виртуализированный список.

**⏱ T-17. Воспринимаемая скорость.** Аватар реагирует в том же кадре, что и отправка сообщения
(кивок, «думаю»): реакция за 16 мс, даже если звук — через 700 мс. Опционально: если TTFA выше
порога — заранее синтезированное междометие («Хм…», «Так…»).

## Как измеряем

- Каждый ход получает `turn_id`; каждая стадия открывает span
  (`telemetry.span("llm.first_token")`) с `time.perf_counter_ns()`.
- Спаны пишутся в `logs/traces.jsonl` и уходят в UI на панель метрик (FR-15).
- `tools/bench_latency.py` прогоняет `bench/prompts_ru.jsonl` (30–50 реплик: короткие, средние,
  длинные, о памяти) N раз с прогретым кэшем и в «сценарии диалога» (последовательные ходы);
  выводит p50/p95/max по каждой метрике и строке бюджета, сравнивает с `bench/baseline.json`.
- Регрессия p95 > 15 % относительно baseline — провал (ручной гейт или CI на машине с GPU).
- PR, затрагивающий горячий путь, содержит таблицу «до/после» (R-39).
